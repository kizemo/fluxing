# 0059. item_key 对服务端不透明：以口令派生的 HMAC 身份替代明文词条

- 状态：已接受 (accepted)
- 日期：2026-11-11
- 关联：ADR 0039（云端账号与多端同步总体架构）、ADR 0054（客户端密钥派生与盐策略）、ADR 0055（同步引擎调度与收敛）、ADR 0057（item_key 的 TAB 契约）、spec 100 `tasks.md` T601 / T603
- 代码：`WeaselServer/Cloud/CloudSyncService.{h,cpp}`（改）
- 测试：`test/TestFluxingCloud/TestFluxingCloud.cpp`（AC-07 断言 +7 条）
- 探针：`scripts/cloud/live-e2e-probe.mjs`（改，身份算法第三份独立实现）

## Context

批次 AN 的 T603 合规核查给出 **AC-07 不通过**：D1 `sync_items.item_key` **明文存放 `<词典名>\t<词条>`**。词条本身就是用户的隐私内容 —— 「服务端存储无明文词条」这条判据在 D1 侧不成立，与「端到端加密、服务端零知识」的产品承诺直接冲突。

原 `item_key` 身兼三职，是缺陷的根源：

| 职责 | 需要什么 |
|---|---|
| D1 主键的一半（`WHERE user_id=? AND item_key=?`） | 一个**稳定**的身份 |
| HLC 守卫的比较基准 / `accepted`·`skipped` 回传 | 同上 |
| R2 对象键（`u/<userId>/<itemKeyHashHex>`） | 同上 |
| **客户端合并时还原「哪个词典的哪个词条」** | **明文** |

只要服务端拿到身份就能干活，而明文只在客户端内部才需要 —— 前两列要的其实是**稳定性**，不是**可读性**。

曾评估两个方案：

- **方案 A**：新增 `item_key_cipher` / `item_key_nonce` 两列，身份仍用明文键、密文另存，协议升 v2。代价 = `ALTER TABLE` + 服务端改造 + 重新部署，且**旧行无法回填**（服务端算不出 HMAC），仍需迁移。否决。
- **方案 K（本 ADR）**：只改客户端送出的身份形态 —— 服务端把 `item_key` 当**不透明字符串**，明文键搬进**已加密载荷**内部。

服务端契约现状是「`item_key` 只做 `assertHeaderString(item_key, MAX_ITEM_KEY_BYTES=512)` + 等值比较 + 原样回传」，**没有任何语义解析** ⇒ 换成一个 64 字符的十六进制串天然合法，**零服务端改动、零表结构改动、零重新部署**。

## Decision

1. **身份 = MAC，不是裸哈希。** 线上 `item_key` 改送

   ```
   item_key_id = lowercase_hex( HMAC-SHA256( mac_key, utf8(item_key) ) )
   mac_key     = HKDF-SHA256( enc_key, salt = 32 × 0x00, info = "fluxing-itemkey-mac-v1", 32 字节 )
   enc_key     = 由用户口令派生的同步密钥（ADR 0054）
   ```

   **不能用裸 SHA-256**：词条熵极低（常用词 + 固定词典名），裸哈希可被字典穷举反查；MAC 密钥由用户口令派生 ⇒ 无口令时**无法**枚举 ⇒ 满足 AC-07「无口令不可还原」。info 串带 `v1`，为将来换算法留位。

2. **明文键搬进 AEAD 覆盖范围。** 加密前的明文载荷改为长度前缀封包：

   ```
   [4 字节大端 key_len][utf8 item_key][utf8 entry.payload]
   ```

   **用长度前缀而非分隔符**：词条可能含任意字节（**含 TAB** —— ADR 0057 刚刚把 TAB 定为合法字符），任何分隔符方案都不可靠。AAD 也随身份一起换：`BuildAad(item_key_id, type, hlc…)`，即 AAD 从此绑定的是**身份**而非明文。

3. **Pull 侧必须重算 MAC 自校验。** 解开封包拿到明文 `entry.key` 后，重算 `ComputeItemKeyId(enc_key, entry.key)` 与 `item.item_key` 比对，不等则整条丢弃并计错。这堵的是「A 的密文 + B 的身份」替换攻击 —— 没有这步，服务端（或被改写的 D1 行）就能把一条密文挂到另一个身份下，客户端仍会照信。

4. **每次调用重算，不做函数级缓存。** `ComputeItemKeyId` 在循环内每条调一次（1000 条约 4 ms 的 HKDF 开销），换取的是**不需要在 6 个 return 路径上分别清零 `mac_key`**。零知识代码里「少一处密钥生命周期管理」比 4 ms 值钱。

5. **旧数据一次性清空，不做兼容分支。** 旧行的 AAD 用的是明文身份 ⇒ 在方案 K 下**必然解不开**；且服务端算不出旧行的 MAC ⇒ **无法回填**。兼容旧格式等于永久保留一条「服务端能看到明文」的旁路，与 AC-07 的意图相反。已知线上仅有测试账号数据且 `ROWS=0`，直接清空。

## Consequences

- ✅ **AC-07 的客户端侧判据已实测通过**（`tmp/AO-probe-closure-2.log`）：线上身份是 64 位小写十六进制，且**不含**词典名 / 词条子串（`userdb` / `探针词条` 均 0 命中）。
- ✅ **服务端零改动**：不改代码、不改表结构、不重新部署。`MAX_ITEM_KEY_BYTES=512` 对 64 字符绰绰有余。
- ✅ D1 与 R2 两侧同时脱敏：D1 只有 MAC 身份，词库名与词条只存在于 AEAD 密文内部。
- ✅ 单测从 **446 → 453 PASS / FAIL=0**；探针新增 3 条 AC-07 断言（身份 64-hex / 身份 ≠ 明文 / D1 无明文残留行）。
- ⚠️ **旧行不可解读**：方案 K 上线前推送的条目必须清空（见决策 5）。若将来有真实用户数据，迁移口径是「让旧行自然过期 + 客户端重推」，不是原地解密。
- ⚠️ **身份不可跨账号共用**：`mac_key` 由 `enc_key` 派生，而 `enc_key` 由口令 + 邮箱确定性派生（ADR 0054）⇒ 同一用户在不同设备上算出的身份**一致**（这是同步的前提），但换口令即换身份。口令重置 = 全量重推，与原设计一致。
- ⚠️ **身份长度写死在契约外**：服务端仍允许最长 512 字节，任何在服务端按「64 位 hex」做假设的改动都会把这条不透明契约重新打穿。审计口径写在 `CloudSyncService.h` 的 AC-07 设计块注释里。
- ✅ 可回退：客户端把 `item_key` 改回明文键、AAD 改回明文、载荷改回裸 payload 即恢复旧行为（但会把 D1 明文词条重新打回来）。
