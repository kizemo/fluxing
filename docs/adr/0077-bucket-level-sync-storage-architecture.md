## Context

### 0. 为什么现在必须改架构

【实测】2026-11-24 12:04（北京时间）生产 D1 读数：`rows_written_24h = 33,043`、`rows_read_24h = 9,083,789`、`write_queries_24h = 13,110`、`database_size = 19,255,296`、`num_tables = 8`。

【实测】D1 免费额度是**每数据库（全局）**、**按行写入**计、**UTC 日重置**、**硬失败**（`code 7500`）。一次全量首导 = 54,536 条 ⇒ 写放大后约 10.9 万行 ⇒ **一次首导即打爆单日 10 万行额度** ⇒ 该库内**所有**账号的所有写操作一起失效（含真实用户登录要写的 `refresh_tokens`）。

【实测】`rows_written_24h` 面板指标是**滚动 24h 窗口**，与 UTC 日不等价（12:04 读 33,043 vs 09:35 读 79,941 即证）。

【实测】`sync_items` 当前 40,061 行 ⇒ 一行一个词条 ⇒ **D1 行数 ≡ 词条数**。这是额度被烧穿的**唯一根因**：D1 被当成词条仓库用，而它每天只有 10 万行。

### 1. 写放大已修，但架构没变

ADR 0076 的 D2-5a-9（语义指纹）已修掉「每轮同一批词条被误判为本地改动 ⇒ 每轮重分配新 HLC ⇒ 每轮全量重写」的放大源。
但**架构层面的 1 : 1 关系仍在**：`sync_items` 一行 = 一个词条 ⇒ 只要用户新增 N 个词条，D1 就必须写 N 行（重推还要 ×2，因为 `DELETE+INSERT`）。

⇒ **稳态零写**成立（客户端不再每轮重推），但**首导 / 重建 / 换机**仍是 O(词条数) 行写入，**免费额度扛不住规模化首导**。

### 2. 免费额度口径（官方）

| 资源 | 免费额度 | 我们的用量级 |
|---|---|---|
| D1 行写入 | 10 万行 / 日（UTC 重置，硬失败） | 首导 10.9 万行 ⇒ **单次打爆** |
| D1 行读取 | 500 万行 / 日 | 9.08 万行/轮 × 约 100 轮/日 ⇒ **已超** |
| D1 存储 | 5 GB | 19 MB ⇒ 富余 |
| Workers Paid | $5/月 ⇒ 首 5000 万行/月（含），读 250 亿行/月（含） | 可覆盖，但**未拍板** |

【推断】D1 行写入是**唯一**硬瓶颈（读写比差 1000 倍）⇒ 改架构的**唯一必要目标**是**把 D1 行数与词条数解耦**。

### 3. 硬约束（不可协商）

1. **E2E 不变量**：服务端只见密文，不解密、不解析明文、不比较内容（ADR 0039 / 0076 I8）。
2. **条目级 AAD 不得改动**：`aad = item_key | type | hlc_ms | hlc_counter | device`（`include/FluxingCloudEnvelope.h`）。这是老密文可验证性的根基。
3. **条目级 HLC 必须保留**：客户端 `RemoteWins` 是**条目级**裁决（`CloudSyncService.cpp` 的 `RemoteWins`）⇒ 桶化后若丢掉逐条 HLC，回退/乒乓风险回归。
4. **无协议版本协商**：客户端与服务端**没有任何 version / capability 字段**（取证报告 §3.5）⇒ 灰度只能靠**独立 URL 路径**。
5. **`server_seq` 语义随索引行变化**：现在是 `sync_items.id`；改桶后是桶行 id ⇒ **编号空间变化** ⇒ 侧车游标必须重置。
6. **R2 单对象 put 慢**：ADR 0074 实测单条 put ≈ 626–706 ms，并发 6 ⇒ 64 条 ≈ 7.5 s。桶大小直接决定单轮传输时长。
7. **写预算护栏是每账号口径**，D1 免费额度是每数据库（全局）口径（ADR 0076 已如实登记）⇒ 桶化**不解决**全局口径问题，只是把单账号放大源降下来。

## Decision

### D1 —— 目标架构：D1 从「逐条索引」降为「设备 × 桶」双维索引，词条包落 R2

我们把「一个词条一行」改成「**一个（设备 × 桶）一行**」，桶内容作为一个密文 blob 整体落 R2：

```
D1  sync_buckets(id AUTOINCREMENT, user_id, device_id, bucket_key,
                 hlc_ms, hlc_counter, hlc_device,
                 r2_key, cipher_len, item_count, updated_at)
    UNIQUE(user_id, device_id, bucket_key)
    INDEX (user_id, id)
```

- **写入量**：首导 = 设备数 × 桶数 行（默认 1 设备 × 64 桶 ⇒ **128 行**，替代 54,536 行 ⇒ **约 425 倍改善**）；
  稳态每轮 = 变更桶数 × 2 行（`DELETE+INSERT`，沿用 ADR 0076 D2-4 的既有口径）。
- **D1 行数与词条数彻底解耦** ⇒ 达成「D1 写入 O(用户数)」的目标。
- **R2 对象数** = 设备数 × 桶数（桶内同 key 覆盖 ⇒ 存储不随轮次增长）。

### D2 —— 桶成员：固定子集，与内容无关

桶 = 「**词典名** + **条目哈希分片**」的固定子集：

```
bucket_key = MAC(enc_key, "bucket:" + dict_name + ":" + shard)      // 十六进制，与 item_key 同一套派生口径
shard      = sha256(item_key)[0] >> 2                                // 固定 64 个一级分片
```

- 桶成员**只由 item_key 决定**，与「内容变没变」无关 ⇒ **改一条词条只重写 1 个桶**（不重写整册）。
- `bucket_key` 是客户端用口令派生的 MAC ⇒ **服务端看不见词典名**（延续 ADR 0059 的不透明身份口径）。
- 分片数固定 64（可配）。桶内条目上限 **4096**；超限时客户端**降级到老端点逐条推**（老端点在灰度期常在）⇒ 不实现动态二级分片。
- 桶大小与 R2 吞吐的权衡见 D9。

### D3 —— 桶 blob 格式：既有条目级信封文本块直接串接，**不做桶级二次加密**

桶 blob = **N 个既有 8 行信封文本块直接串接**（`include/FluxingCloudEnvelope.h` 的 `SerializeEnvelope` 产物：首行 magic `v1`，其后 7 行 `name\tvalue` 制表符分隔，字段序 `item_key / type / hlc_ms / hlc_counter / device / nonce / cipher`，每块以 `\n` 结尾 ⇒ 串接后共 8N 行）。

- **零新增格式、零新增 AAD**：客户端拆包 = 按 8 行切块后逐块 `ParseEnvelope`；条目级 AEAD 的 AAD（`item_key | type | hlc_ms | hlc_counter | device`）**逐字不变** ⇒ **老密文在新协议里仍可逐条验证**。
- **服务端不解析 blob**（沿用 ADR 0076 I8「服务端不解析信封 8 行文本」的口径）⇒ 桶级 HLC 由**客户端**计算并随请求上报，服务端只存不校。
- **不引入桶级 nonce / 桶级 AAD** ⇒ 取证报告 §4.2 草案里的桶级 AEAD 被本决策**否决**（AAD 混用风险归零、收益为零）。
- 服务端只见密文 ⇒ E2E 不变量保持。

### D4 —— HLC 守卫双层：服务端桶级，客户端条目级

- **服务端权威** = 桶级 HLC（该桶内所有条目 HLC 的最大值，沿用 `compareHlc` 的同一套规则）。
  守卫：服务端已存桶级 HLC **≥** 客户端送上来的桶级 HLC ⇒ **整桶跳过**（不写 R2、不写 D1、不推进 `server_seq`）⇒ 保住「不写放大」这最后一道服务端防线。
- **条目级 HLC 保留在 blob 内** ⇒ 客户端 `RemoteWins` 逐条裁决能力**不变** ⇒ 取证报告 §6.3 风险 2 被消解。

### D5 —— 每设备独立视图：同桶不同设备互不覆盖

D1 行含 `device_id` ⇒ 设备 A 推的桶 X 与设备 B 推的桶 X 是**两行、两个 R2 对象**。

- 客户端拉取时拿到**所有设备**的桶视图，按**条目级 HLC** 合并 ⇒ **无 lost update**（A 不会盖掉 B 的桶）。
- 桶级守卫只在**同一设备的同一桶**上生效 ⇒ 单设备单进程 ⇒ 不会自相覆盖。
- 代价：D1 行数上界 = 设备数（ADR 0076 D3 限 32）× 桶数（64）= 2048 行/账号 ⇒ 可控且可诊断。

### D6 —— 灰度：独立 URL 路径，老端点原样不动

新增端点（服务端先上，老客户端不受影响）：

```
POST /v1/sync/buckets/push
GET  /v1/sync/buckets/pull
```

- `/v1/sync/push`、`/v1/sync/pull` **保持原语义、逐字不动** ⇒ 生产零风险；新客户端走新路径。
- 无版本协商 ⇒ 只能靠路径分流（取证报告 R5）。
- **`server_seq` 语义从「条目行 id」变为「桶行 id」** ⇒ 客户端侧车**必须升版为 v2 并强制重置 `seq = 0`**（否则老游标会被解释成另一个编号空间 ⇒ 漏拉或重拉全量）。

### D7 —— pull 响应契约：顶层三字段同名同义保留

```json
{
  "buckets": [
    { "bucket_key": "<hex>", "device_id": "<hex>", "hlc": {"ms":0,"counter":0,"device":""},
      "cipher": "<base64 桶 blob>", "item_count": 852, "server_seq": 12345 }
  ],
  "next_cursor": "<base64url(id)|null>",
  "has_more": false,
  "server_seq": 12345
}
```

- 顶层 `server_seq` / `next_cursor` / `has_more` **必须保留同名同义**（客户端 `ParsePullResponse` 依赖）。
- `limit` 语义从「条目数」变「**桶数**」（默认 50 / 上限 100，沿用现有常量口径）。

### D8 —— 写预算护栏口径换表

- `used` 的 COUNT 从 `sync_items` 换到 `sync_buckets`；`planned` 的估算对象从「条目数」变「桶数」（桶首次出现 1 行 / 已存在 2 行）。
- 口径注释（`src/sync.ts` 的护栏小节）**必须同步改写**，否则会继续对外宣称「80,000 行 ≈ 允许一次全量重推」。
- 环境变量保留旧名兼容，新增 `WRITE_BUDGET_BUCKETS_PER_DAY`；旧阈值在桶化后已属巨量，默认值需重估。

### D9 —— 桶大小是「D1 行数 ↔ R2 吞吐」的显式权衡

【实测】ADR 0074：R2 单条 put ≈ 626–706 ms，并发 6 ⇒ 吞吐约 8.6 条/s。

| 桶大小（条） | 首导 D1 行数（1 设备 × 54,536 条） | 稳态单桶 put 时长（并发 6） |
|---|---|---|
| 64 | 852 行（≈ 64×改善） | ≈ 7.5 s |
| 256 | 214 行（≈ 255×改善） | ≈ 30 s（超 WinHTTP 30 s 超时） |
| 512 | 108 行（≈ 505×改善） | ≈ 60 s（超） |

⇒ **默认桶大小取 64 条**（首导 852 行，稳态单桶 ≈ 7.5 s 在超时内）。
提高 R2 并发度可放宽该约束，但**并发度提升需先实测**（ADR 0074 的 6 是当时选值）⇒ 登记为后续批次候选。

### D10 —— healed 自愈的粒度风险（已知边界，不在本次解决）

桶化后 R2 对象缺失 ⇒ 自愈只能删**桶行** ⇒ 连带丢掉该设备该桶的全部条目（现状只丢一条）。
本批**接受**该风险（桶很小，损失面有限），并登记为 **BR-①g** 候选（blob 内保留条目级索引，或客户端做部分恢复）。

### D11 —— 实施分期

- **本批（BR-①f）= 服务端先行**：新表 + 新端点 + 护栏换表 + 单测 + 门禁 + 部署。
  老端点不动 ⇒ **生产零风险**，可独立验收。
- **下一批（BR-①g）= 客户端**：分桶打包 / 拆包、桶级 HLC 分配、侧车 v2 升版与 `seq` 重置、分页预算第二道闸、打包装机 + 真机判据。
- `sync_items` 表与老端点的**退役**另立 ADR（条件：客户端全面切新端点且 AC-09 连续稳定）。

### 备选方案与否决理由

| 备选 | 否决理由 |
|---|---|
| **直接升级 Workers Paid** | 不改放大源，只是把阈值抬高；D1 行数仍 ≡ 词条数，规模上去后再次打穿；且**用户未拍板**。 |
| **分日 pacing（把首导切成 N 天）** | 首导窗口变成 N 天，用户数据在此期间跨设备不同步；且需要引入调度状态机。BR-①e 已拍板「维持现状」，本 ADR 不推翻。 |
| **每设备一个全量 blob（D1 1 行/账号）** | D1 行数最优，但**稳态每次改一条就要重传全量词典**（10~40 MB），出网流量与 30 s 超时都扛不住；桶化把这个代价限制在 1 个桶内。 |
| **桶级二次 AEAD（桶 nonce + 桶 AAD）** | 引入第二套 AAD ⇒ 混用风险与老密文验证问题；条目级 GCM tag 已提供逐条完整性 ⇒ 收益为零、风险为正。 |
| **服务端在密文域做桶内合并 / 去重** | 服务端无密钥，AAD 含 hlc 且 nonce 随机 ⇒ 密文域无法去重（ADR 0076 D2-2 已关闭该路线）。 |

## Consequences

### ✅ 变得更容易

- D1 行写入与词条数**解耦** ⇒ 首导从 ~10.9 万行降到 852 行量级 ⇒ 免费额度从「单次打爆」变为「可支撑规模化首导」。
- 稳态每轮 D1 写 = 变更桶数 × 2 行 ⇒ 接近 0。
- 服务端只见密文、条目级 AAD 不变 ⇒ E2E 语义零变化，无需重新设计密钥体系。

### ⚠️ 变得更难

- **客户端要实现桶打包 / 拆包 + 桶级 HLC 分配 + 侧车 v2 升版**（下一批 BR-①g）。
- **首导传输仍是全量词典**（密文不可压缩）⇒ 家宽上行 10 Mbps 下 40 MB ≈ 32 s ⇒ 必须分批 + 后台完成，客户端 30 s 超时（`CloudTransport.h`）需要按批次规避。
- **R2 put 吞吐成为新瓶颈**（D9）⇒ 桶大小与并发度成为需要实测的参数，不是自由选择。
- **healed 自愈粒度变粗**（D10，BR-①g 候选）。
- **出网流量**成为次级瓶颈（免费 100 GB/日 ⇒ 约 26 个活跃全量同步用户/日）⇒ 桶化把流量从「稳态每轮全量」降为「稳态每轮 1 桶」，但首导仍是全量。

### 🔒 新增约束

- 任何对桶 blob 格式的改动都是**协议级**改动 ⇒ 必须**同时**改服务端 + 客户端 + 两侧单测，且必须走 ADR。
- 桶级 HLC 与条目级 HLC **必须同时存在**；只留其一 ⇒ 必然回退或乒乓。
- `server_seq` 编号空间在两套端点间**不同** ⇒ 侧车必须按协议版本分区，**禁止**跨版本复用游标。

### 🔁 可逆性

**部分可逆**：新端点与新表是**增量**的，老端点与 `sync_items` 保持原样 ⇒ 客户端出问题时可立即切回老端点（客户端侧开关）。
`sync_buckets` 表可 `DROP TABLE` 回滚。**不可逆的部分**：一旦客户端写入桶级数据，`sync_items` 的历史行**不能自动迁回** ⇒ 退役必须走「双写 → 校验 → 切读 → 退役」的显式流程。

## 与既有决策的关系

| 既有决策 | 关系 |
|---|---|
| ADR 0039（E2E + 合并落客户端） | **继承**：服务端只见密文、合并落客户端不变。 |
| ADR 0059（item_key 不透明 MAC 身份） | **继承并扩展**：桶键沿用同一套 MAC 派生口径。 |

| ADR 0076 D2-4（`DELETE+INSERT`） | **继承**：桶行同样用 `DELETE+INSERT` 拿新 id。 |
| ADR 0076 D3（设备上限 32） | **继承**：D1 行数上界 = 设备数 × 桶数（D5）。 |

## 客户端段（批次 BR-①g）—— D12…D22

> 本段是 **BR-①g 客户端桶化**的决策条目，与服务端段 D1–D11 并列但**互不覆盖**：
> D1–D11 逐字不动；本段只在**服务端不感知**的地方做客户端侧决策。
> 客户端实现落点：`WeaselServer/Cloud/CloudBucketSync.{h,cpp}`（纯函数层）+ `CloudSyncService.{h,cpp}`（编排层）。

### D12 —— 阶段状态机：老端点 → 双写 → 校验 → 切读 → 退役

五个阶段，**由客户端侧一个开关驱动**，服务端无感知：

| 阶段 | 含义 | 推 | 拉 | 老端点 |
|---|---|---|---|---|
| **0** | 老端点单跑（**默认**） | 老端点 | 老端点 | 唯一路径 |
| **1** | 双写 | 老端点 **+** 桶端点 | 老端点 **+** 桶端点 | 仍活跃 |
| **2** | 双写 + 交叉校验 | 同阶段 1 | 同阶段 1，**并**比对两路结果 | 仍活跃 |
| **3** | 切读 | **只推桶端点** | **只拉桶端点** | **完全不发** |
| **4** | 老端点退役 | 桶端点 | 桶端点 | 已下线 |

- **生效口径**：环境变量 `FLUXING_CLOUD_SYNC_BUCKET_PHASE` **优先**；否则读侧车里的 `phase` 字段；两者都无 ⇒ **阶段 0**。
- **环境变量生效时写回侧车** ⇒ 阶段值**持久化**在侧车里（下次启动若无环境变量，仍按侧车值走）。
- **回滚 = 把环境变量设为 `0` 跑一轮**（不改代码、不重装、不删数据）——这是本段最重要的一条可运维性约束。
- **阶段不自动递增**：每次跃迁必须由人工显式设置环境变量或改侧车 `phase` ⇒ 杜绝「客户端自己滚到下一阶段」的不可控切换。
- **理由**：无版本协商字段（硬约束 4）⇒ 只能靠客户端侧开关灰度；阶段分离让「双写验证」与「切读」之间有**可观察的证据窗口**。

### D13 —— 侧车 v2：双编号空间 + 桶行 + 阶段位，**必须能读 v1**

- **头行**：`#fluxing-cloud-sync-v2`（v1 是 `#fluxing-cloud-sync-v1`）。
- **保留 v1 的字段**（语义逐字不变）：
  - `seq` —— **老端点**（条目级）游标；
  - `keyfp` —— 口令指纹（密钥轮换判定）；
  - `row` —— **条目级**语义指纹行（`item_key` / `ms` / `counter` / `device` / `payload_hash`，`payload_hash` 仍是 `s2:` 口径）。
- **新增字段**：
  - `bseq` —— **桶端点**游标；**编号空间独立于 `seq`**、**强制从 0 起**（服务端 `sync_buckets.id` 与 `sync_items.id` 是两个 AUTOINCREMENT 序列，跨空间比较无意义）。
  - `phase` —— 阶段位（0…4，见 D12）。
  - `brow` —— 桶行：`bucket_key` / `ms` / `counter` / `device` / `item_count` / `fingerprint`。
- **必须能读 v1**：读到 v1 侧车 ⇒ **phase = 0、bseq = 0、无 brow** ⇒ 升级后的第一轮**行为与升级前逐字等价**（老端点单跑），桶化需显式开阶段 1。
- **理由**：服务端老端点在阶段 0–3 期间**仍活跃**，条目级游标 `seq` 仍必须维护 ⇒ 不能像 ADR 0077 D6 设想的那样「强制重置 `seq = 0`」；**改为并列 `bseq`**，两套游标互不干扰、各自从自己的编号空间推进。**这是对 D6 的一处偏离**，理由记录于下方「偏离登记」。

### D14 —— 桶键派生：加密域 HMAC 摘要字节 + **独立 HKDF 标签**

- **偏离 ADR 0077 D2 原文**：D2 写 `shard = sha256(item_key)[0] >> 2`（**明文**摘要派生）。本决策**不用**明文 `sha256(item_key)`。
- **理由**：明文派生可被**字典穷举反推** —— 攻击者对候选词表逐个算 sha256 就能反推「哪个词条落在哪个桶」，进而推断用户的词库内容分布 ⇒ 违反 ADR 0077 硬约束 1（E2E：服务端只见密文、不可推出明文分类）与 ADR 0059 的不透明身份口径。
- **做法**：分片索引取**加密域** HMAC 摘要字节；桶键由**独立 HKDF 标签** `fluxing-bucketkey-mac-v1` 派生的 MAC 密钥再算一次 MAC ⇒ **桶键与 item_key 身份不可互推**，也不与 `fluxing-itemkey-mac-v1` 复用同一把密钥。
- **桶键形态**：**64 位小写十六进制**（HMAC-SHA256 = 32 字节）。
- **客户端落点**：`CloudBucketSync.h` 的 `DeriveBucketMacKey` / `ComputeBucketShard` / `ComputeBucketKeyId`。

### D15 —— 分桶粒度：一级 64 片 × 二级 16 片 = **1024 桶 / 词典**

- **偏离 ADR 0077 D2 原文**：D2 写「固定 64 个一级分片」；D9 的「每桶 64 条」是**另一套**参数。两处口径互斥已在 spec 102 §9 Q1 登记。
- **本决策取值**：**1024 桶 / 词典**（64 × 16）。
- **理由**：本地条目全集 94,604 条 ÷ 1024 ≈ **92 条 / 桶**（仅按未上云的 54,536 条计则 ≈ 53 条 / 桶），**两个口径都远低于**服务端 `MAX_BUCKET_ITEMS = 4096`（余量约 44–77 倍）⇒ 常态不会触发降级。桶数取 1024 而非 64，是为了让**单桶 blob 足够小**，把 R2 单对象 put 时长压进客户端 30 s 超时窗（D9 的实测换算：桶 64 条 ≈ 7.5 s；桶 852 条 ≈ 100 s ⇒ 不可行；**本粒度（≈92 条/桶）的单轮时长未实测 ⇒ 见 AC-112 四项数值，记「未判定」**）。桶数越多 ⇒ D1 首导行数越多，1024 行相对 54,536 行仍是 **约 53 倍**改善，且远低于 D1 免费额度 10 万行/天 ⇒ 不需要分日 pacing（见「补推分批策略」）。
- **桶数与 D1 行数的关系**（服务端侧）：首导 D1 行数 = 设备数 × 桶数（1 设备 × 1024 桶 = 1024 行）；存量上界 = 设备数上限 32 × 1024 = 32,768 行/账号（沿用 D5 口径）。

### D16 —— 桶 HLC = 桶内条目 HLC 最大值，且**必须严格大于**侧车已存桶 HLC

- 桶级 HLC 取桶内所有条目 HLC 的**最大值**（`AggregateBucketHlc`）。
- **关键加固**：上报的桶 HLC 必须**严格大于**侧车已存桶 HLC ⇒ 用 `MakeHlcStrictlyGreater` 抬升。
- **理由**：服务端 HLC 守卫是「已存 ≥ 上报 ⇒ 整桶跳过」。若桶内容变了但条目 HLC 没变大（例如同一 HLC 下内容被替换），服务端会把**真实变更整桶 skipped** ⇒ 静默丢数据。抬升是这条路径的唯一兜底。
- 桶级 HLC 与条目级 HLC **并存**（条目级仍在 blob 内）⇒ 硬约束 3（条目级 HLC 必须保留）不变。

### D17 —— 桶内容指纹用**语义口径**（`s2:` / `SemanticHashHex`）

- 桶指纹由桶内条目的 `item_key` + **语义指纹**（`s2:` 前缀的 `SemanticHashHex`）+ 条目 HLC 拼接后取 SHA-256（`BucketFingerprint`）。
- **不用**密文哈希、**不用**全载荷哈希。
- **理由**：rime 每轮同步回写本地词典会重算 `d=` / 改写 `t=` ⇒ 全载荷哈希**每轮都变** ⇒ 桶指纹每轮都变 ⇒ 每轮重推 ⇒ **写放大回归**（这正是 ADR 0076 D2-5a-9 根治掉的问题，不能在桶级重犯）。
- 指纹口径与条目级侧车 `row.payload_hash` **同源**（同一个 `SemanticHashHex`）⇒ 单一真相源。

### D18 —— 桶内容 = merged 本地视图**全集**按 (词典名, 分片) 分组后的整桶

- 桶内容取**合并后的本地视图全集**按 (词典名, 分片) 分组 ⇒ 每桶是**整桶**。
- **理由**：服务端是 `DELETE+INSERT` 覆盖语义 ⇒ 只推变更条目会**丢掉同桶其它条目**。
- **只推指纹变化的桶** ⇒ 稳态零写（指纹不变的桶既不推也不产生 D1 写）。
- 与 D17 联动：指纹是「要不要推」的判据；HLC 是「服务端会不会接受」的判据。

### D19 —— 桶 blob = 既有 8 行信封文本块串接，**不新增桶级 nonce / 桶级 AAD**

- `PackBucketBlob` / `UnpackBucketBlob` 串接/拆分既有 `SerializeEnvelope` 产物 ⇒ **零新增格式、零新增 AAD**（D3 逐字落实）。
- 条目级 AAD（`item_key | type | hlc_ms | hlc_counter | device`）**逐字不变** ⇒ 老密文在新协议里仍可逐条验证。
- 桶拉取解包后**复用同一条解密路径**（与 `OpenItemsTolerant` 同语义：解不开只计数；userdb 类额外形态校验并**单独计数 malformed`）⇒ **不新写第二套解密实现**（宪法 R7 单一真相源）。
- 客户端落点：`CloudBucketSync.h` 的 `PackBucketBlob` / `UnpackBucketBlob`；解密侧复用 `CloudSyncService.cpp` 的 `OpenItemsTolerant`。

### D20 —— 分批：推 ≤ 64 桶/请求；拉 ≤ 100 桶/页、单轮页数上限见 D27（动态计算，硬上限 32 页）

- **推**：单请求 ≤ **64 桶**（服务端 `MAX_PUSH_BUCKETS`）⇒ 1024 桶首导 = **16 个请求**。
- **拉**：单页 ≤ **100 桶**（服务端 `MAX_PULL_LIMIT`），**单轮页数上限 = max(16, 词典数 × 11 + 2)**，且**不超过 32 页**（硬上限，见 **D27**）⇒ 单词典时 16 × 100 = 1600 ≥ 1024 ⇒ **一轮必须能扫完 1024 桶**。
- **理由（硬约束）**：若一轮扫不完 ⇒ 客户端的「库存未证实」闸门（R2 语义）会**永久压制推送** ⇒ 新词条永远上不了云。客户端现有条目级分页是 `kPullPageLimit = 100` × `kMaxPullPages = 10` = 1000 条；桶化后单词典取 16 页（1024 桶 ⇒ ⌈1024/100⌉ = 11 页，留余量）。
- 单轮拉取上限（单词典 ≥ 16 页 / 硬上限 32 页）是**桶级专用**，不改条目级分页常量（老路径仍需 10 页 × 100 条的既有语义）。
- **多词典时按词典数动态算**（见 **D27**）：单轮页数上限 = **max(16, 词典数 × 11 + 2)**，且**不超过 32 页**（硬上限）⇒ 固定 16 页**只在单词典时成立**；多词典固定 16 页 ⇒ 扫不完库存 ⇒ 「库存未证实」闸门永久压制推送。**词典数 ≥ 3 时该公式即触到 32 页硬上限** ⇒ 4 词典及以上可能扫不完库存 ⇒ 该情形列为待实测项（见 spec 103 Q2；硬上限是客户端常量，调整不需服务端改动）。

### D21 —— 超限降级：某桶 `item_count > 4096` 或 blob > 4 MiB ⇒ 该桶走老条目端点推

- 单桶超 `MAX_BUCKET_ITEMS`（4096）或 blob 超 `MAX_BUCKET_BLOB_BYTES`（4 MiB）⇒ 该桶**降级走老条目端点逐条推**，其余桶照常走桶端点。
- **理由**：服务端桶端点会拒收超限桶（`validatePushBucket`），若不降级则整批失败 ⇒ 一个超限桶拖垮全部桶。
- 客户端落点：`CloudBucketSync.h` 的 `kBucketMaxItems` / `kBucketMaxBlobBytes`。

### D22 —— 补推策略：桶化后**不需要分日 pacing**

- 桶化后首导 ≈ **1024 桶** ⇒ D1 写入 ≈ **1024 行**（约 **53 倍**改善）⇒ 单日 10 万行额度不是约束 ⇒ **不需要**分日 pacing。
- **不推翻** BR-①e「维持现状」—— BR-①e 拍板的是**条目级**首导（约 5.4 万条 / 约 10.9 万行）的分批策略；桶化后该量级降到 1024 行 ⇒ **前提已变**。
- 只需两层保护：**客户端侧分批**（每请求 ≤ 64 桶）+ **失败续传**（没推成功的桶不写 `brow`，下一轮继续）。
- 详见下方「补推分批策略」小节。

### D23 —— 分桶口径的拍板结论（**回答 spec 102 §9 Q1**）

spec 102 §9 **Q1** 记的是 ADR 0077 内部「桶成员」节（固定 64 个一级分片 ⇒ 64 桶、每桶 ≈ 852 条）与「桶大小」节（默认每桶 64 条 ⇒ 852 桶）**两者互斥，需拍板**。

**本批拍板结论（2026-11-25）**：

- 选「**每桶条目数**」这一层为口径。
- 「**64**」解释为**一级分片数**，并在其下再分**二级 16 片** ⇒ **1024 桶 / 词典**。
- 每桶实际条目数 ≈ **53** 条（54,636 ÷ 1024），**远低于**服务端 `MAX_BUCKET_ITEMS = 4096`。
- 首导索引行数 **1,024**（替代 54,536，约 **53 倍**改善）。
- **理由**：① 1024 是 2 的幂 ⇒ 分片均匀、无余数偏斜；② 桶更小 ⇒ 单桶 R2 put 更快 ⇒ 更安全地落在客户端 30 s 超时窗口内；③ 索引行数与 ADR D9 的「852 行」档位**同量级**（1024 vs 852，差约 20%）⇒ **不改变额度结论**。
- **偏离声明**：这**偏离**了 ADR 0077 D9「默认桶大小取 64 条 ⇒ 852 桶」的表述；偏离理由 = **「64」是分片数，不是每桶条目数上限**（D9 与 D2 混用了两个层级，见 Q1）。D9 的「64 条/桶 ≈ 7.5 s」作为**推算档位**仍成立。

### D24 —— 写入量口径必须分两个口径（**回答 spec 102 AC-107**）

任何「写入量下降多少倍」的表述**必须标明是哪个口径**：

| 口径 | 条目级（老端点） | 桶级（BR-①g） | 改善倍数 |
|---|---|---|---|
| **索引行数**（存量 / 每设备） | 54,536 行（`sync_items`） | **1,024 行**（`sync_buckets`） | 约 **53 倍** |
| **D1 实际写行数**（首导，含 `DELETE+INSERT`） | ≈ 54,536 行 | ≈ **2,048 行**（1,024 桶 × 2） | 约 **27 倍** |

- **D1 实际写行数**之所以是索引行数的 2 倍：服务端桶 push 写序是 **R2 put ⇒ D1 `DELETE+INSERT`** ⇒ 每桶约 2 行写（ADR 0076 D2-4 在桶级沿用）。
- **AC-107 上界式**：单请求索引写行数 ≤ **2 × 本轮桶数**；本轮桶数 ≤ **64**（`MAX_PUSH_BUCKETS`）⇒ **单请求上界 128 行**。
- ⇒ 「约 53 倍」说的是**索引行数**；「约 27 倍」说的是**D1 实际写行数**；两者都远低于 D1 免费额度 10 万行/天 ⇒ 结论一致（不需要分日 pacing），但**数字不可混用**。

### D25 —— 序号编号空间（**回答 spec 102 AC-109 · 已由 BR-①g 落实**）

- **申报事实**：桶级序号（`sync_buckets.id`）与逐条序号（`sync_items.id`）**互不可比**（两个独立 AUTOINCREMENT 序列）——已在 ADR 0077 D6 与 spec 102 AC-109 登记。
- **客户端侧对应动作（本批落实）**：
  - 侧车 v2 的桶游标 **`bseq` 独立、强制从 0 起**，**不得默认沿用老游标 `seq`**；
  - 老端点游标 `seq` **继续服务老端点**；两者**互不参照、互不比较、互不推进**。
- **AC-109 状态**：客户端批次**硬前置 ⇒ 已由 BR-①g 落实**（见 D13）。
- **偏离说明**：ADR 0077 D6 原文写「客户端侧车必须升版为 v2 并强制重置 `seq = 0`」；本批**保留 `seq`** 给老端点、另设 `bseq`（理由见「客户端段偏离登记」第 3 条）。**D6 的原意（两个编号空间互不解释）已达成。**

### D26 —— 桶级响应字段集合（**回答 spec 102 AC-108 · 客户端解析器影响评估**）

- 桶级 pull 的桶对象字段**只有**：`bucket_key` / `device_id` / `hlc` / `cipher` / `item_count` / `server_seq` —— **无 `nonce` 字段**（与老端点不同）。
- **客户端影响评估（结论）**：客户端**不能复用**老端点的响应解析器。老端点 `ParsePullResponse` 对每个条目执行 `json::MemberString(doc, index, "nonce", &item.nonce_b64)`，缺 `nonce` 即报「服务器返回的条目缺少 nonce 或 cipher。」⇒ 拿桶响应喂给它会**整批判为非法**。
- ⇒ 桶级解析器**独立实现**并**按桶契约判字段**（桶级 `cipher` 是整桶 blob 的 base64，解包后仍走条目级 8 行信封解析）。
- **对老端点零影响**：`ParsePullResponse` 及其「必填 nonce」判据**逐字不动**（老端点继续按老契约走）。

### D27 —— 拉取页数上限按**本地词典数**动态计算

- **问题**：桶总数 = **词典数 × 1024**。固定 16 页（16 × 100 = 1600 桶）只够**单词典**；多词典时**扫不完库存** ⇒ 客户端「库存未证实」闸门（ADR 0076 D2-5a R2）**永久压制推送** ⇒ 新词条永远上不了云。
- **决策**：拉取页数上限**按本地词典数动态计算**：**单轮页数上限 = max(16, 词典数 × 11 + 2)**，且**不超过 32 页**（硬上限）；单请求桶数 ≤ **64**；单页桶数 ≤ **100**。（与 spec 103 的 AC-203 **逐字同源**，便于两处对账。）
- **理由**：与 D20 的「一轮必须扫完」是同一条硬约束的推广 —— 从「单词典固定 16 页」改为「按词典数动态算」。
- **公式与硬上限的含义**：单词典 ⇒ 16 页（1,600 桶 ≥ 1,024 桶 ⇒ 一轮扫完）；词典数 = 2 ⇒ 24 页；**词典数 ≥ 3 ⇒ 触到 32 页硬上限**（3 × 11 + 2 = 35 > 32 ⇒ 封顶）⇒ **4 词典及以上可能扫不完库存** ⇒ 「库存未证实」闸门会压制推送 ⇒ **需实测「本机常见词典数」**以确认硬上限是否够用（硬上限是客户端常量，调整**不需服务端改动**）。

### D28 —— ADR 0077 D10 的客户端部分恢复（切读阶段的缺失检测）

- **背景**：D10 记录了「healed 自愈粒度变粗」的风险：桶对象缺失时服务端只删**桶行** ⇒ 连带丢掉该设备该桶的**全部条目**。
- **客户端部分恢复**：切读阶段用**远端桶视图**与**侧车**比对 ⇒ 「**侧车已同步但远端视图缺失**」的条目 ⇒ 其所在桶**强制重推**（**即使指纹未变**）。
- **前提（硬闸）**：**本轮库存扫描必须完整**（一轮扫完、`has_more = false`）；扫描不完整时**不做**该判定 ⇒ 避免误判 ⇒ **避免写放大回归**。
- **理由**：这是 D10「风险接受」在客户端侧的补偿手段 —— 云端丢桶时，本机仍保有侧车里的基线，可据此判断「我同步过、但云端没了」。

### D29 —— 每轮桶推行数配额（**单一真相源**；对应 spec 103 **AC-215**）

- **决策**：客户端单轮桶推送有**行数配额**（D1 写行口径）；实现常量 = 头文件注释 = 本条 = spec 103 **AC-215**，四处**逐字相等**。
- **当前实现值 = 2,000 行/轮**（`CloudSyncService.h` 的 `kBucketPushRowsPerRound`；1.3.10 真机轮实测生效值）。
- **候选值（待用户拍板）**：2,000（当前实现 / 真机实测，**推荐**）/ 4,096（早期注释值）/ 8,000（handoff §M.8.4 / §O-1.1 建议值）；**改值必须重出包装机**（常量编译进客户端二进制）。
- **算法**：按声明序累加本轮已推行数，**超限即停**（**不插队、不截断单桶**）；被截断的桶**整桶延到下一轮**，其侧车桶行不更新 ⇒ 下一轮自然续推。单请求桶数仍受服务端 `MAX_PUSH_BUCKETS = 64` 约束。
- **诊断**：配额行 `bucket quota held_unproven=<n> held_quota=<n> rows_pushed=<n> rows_held=<n> quota_rows=<n>` **无条件打印**，且**结构性只在 `PushChangedBuckets` 函数体内** ⇒ 是**唯一可靠的推轮判据**（`bucket phase=` 在 kPullOnly 轮也会打印且 `pushed=0`，不可当推轮判据）。
- **硬约束**：生产写预算护栏 **每账号 20,000 行/日**（handoff §O-1.3）+ D1 免费额度 **每库 100,000 行/日**（全局口径，非每账号）⇒ 客户端闸门是第一道防线，但**不是**平台额度护盾（BR-②′ 全局熔断尚未立项）。
- **已知边界**：桶指纹（brow）目前**不落盘**（handoff §P-H.4）⇒ 稳态零写不成立 ⇒ 现网实测每轮写入量级远高于本配额的设计意图；本配额要在 **brow 落盘修好**之后才回到「首导 / 补偿」定位。
- **编号口径（本 ADR 统一，消除既往混写）**：真机判据 = spec 103 **AC-212**（本 ADR 内部写的 **AC-112** / **AC-203** **均指它**）；**AC-213 / AC-214 为永久退役的悬空引用**（从未定义，**不得引用**）；每轮桶推行数配额 = spec 103 **AC-215**。

### D30 —— 配额记账口径与「尾部桶饿死」（2026-11-25 阶段 2 真机轮读码 + 生产实测坐实）

- **背景**：D29 定了配额值与「超限即停」算法，但**「一行」是怎么算出来的**此前没落到 ADR 里；本轮读码 + 生产真机轮把它坐实了，同时发现 D29 的「自然续推」表述在 brow 未落盘期间**不成立**。
- **每桶 = 2 行**：`EstimateBucketWriteRows(shard_count, has_deletions) = shard_count*2 + (has_deletions?2:0)`（`CloudSyncService.h`）⇒ 一个桶 = **2 行**（服务端按分片先 DELETE 后 INSERT）⇒ 配额 **2,000 行/轮 = 1,000 桶/轮**；候选值 4,096 ⇒ 2,048 桶/轮、8,000 ⇒ 4,000 桶/轮。
- **候选恒为全量分片空间**：诊断行 `rows_pushed=2000 / rows_held=48` 反推候选桶数 = (2000+48)/2 = **1,024** = D15 的 64×16 ⇒ 候选按 `bucket_key` 排序（`std::map` ⇒ **顺序确定且逐轮稳定**）；brow 不落盘期间**每轮候选都是同一批 1,024 桶**。
- **尾部桶饿死（结构性，⚠ 与 D29 的表述冲突，以本条为准）**：`SelectBucketsWithinQuota` **遇超即停、不插队** ⇒ 每轮被送出的永远是**同一批前 1,000 桶** ⇒ **尾部 24 桶永远轮不到**。
  - **生产实测**：阶段 1 落库 704 桶、阶段 2 落库 1,000 桶，**至今 `sync_buckets` 恒 1,000 行 ≠ 1,024** ⇒ 至少 24 桶**从未上云**。
  - **订正 D29**：D29「被截断的桶整桶延到下一轮、下一轮自然续推」**只在「候选集合逐轮变化」时成立**；brow 落盘修好前该表述**不成立**（下一轮还是同一批前 1,000）。修 brow 落盘 + 稳态零写后本项自动缓解。
- **记账口径（诊断行 ≠ 实际写入）**：`rows_pushed` 记的是「**选中**桶数 × 2」，**不是**实际送出/落库行数；推途中途失败（`push_ok=false; break`）时护栏记账**高于**实际写入 ⇒ 方向保守（不危险），但**不得把该数字当成实际写入量**。
- **阶段 1 的「704 / 1,000」缺口（未坐实）**：服务端既未 accepted 也未 skipped（`skipped=0`）、notify 日志无任何错误行 ⇒ 候选成因见 handoff §P-K.4；阶段 2 缺口消失（1,000/1,000 落库）⇒ 非结构性上限。
- **对 D29 判据的补充**：配额行 `quota_rows=` 在**函数体内**打印，轮汇总行 `bucket phase=… pushed=N` 在**调用方**打印 ⇒ **判「一轮推完」必须用汇总行**，用函数内埋点当「动作完成」判据会中途截断该轮（2026-11-25 实测踩坑，见 handoff §P-K.5）。

### D31 —— 每轮桶推行数配额的**唯一值裁定**（2026-11-25 用户拍板）

- **裁定结果**：每轮桶推行数配额 = **2,000 行/轮**（**唯一值**）⇒ 按 D30 的「每桶 2 行」口径 = **1,000 桶/轮**。
- **裁定依据**：① 实现常量 `kBucketPushRowsPerRound = 2000` 已在 1.3.10 真机轮**实测生效**（`quota_rows=2000`）；② 候选 4,096 / 8,000 均**未实测**，改值须改常量 + **重出包装机** + 重跑真机轮；③ 2,000 行/轮 ⇒ 单账号一天最多 10 轮触到 **20,000 行/日**护栏（handoff §O-1.3），护栏不会被桶推送单独击穿；④ D1 免费额度 **100,000 行/日**是**整库全局口径**（非每账号），取值越小越安全。
- **执行方式**：**实现常量保持 2,000 不变** ⇒ 本裁定**未改行为**，**未重出包装机**，与已验证的 1.3.10（`WeaselServer.exe` sha256 `D7DFAC785CB1C2D262716D37DD21C19BDC6C02BD4A688E4CDB8446F519E8EB79`）**运行时行为逐字一致**；本轮只订正**注释与文档口径**（头文件注释 / 本条 / spec 103 AC-215 **四处逐字相等**）。
- **落选候选留档**：4,096 ⇒ 2,048 桶/轮（一轮扫完一个词典的全量补推 ≈ 2,304 行）；8,000 ⇒ 4,000 桶/轮（导入更快但单轮写入上界更高）。二者**仅在 brow 落盘修好、且确需缩短补推轮数时**再评估，届时必须改常量 + 重出包装机 + 重跑真机轮。
- **⚠ 裁定不解除的既有阻塞**：D30 的「**尾部 24 桶永久饿死**」与 spec 103 AC-215 判据②「被截断的桶下一轮被重新选中」**仍未达成**（桶指纹 brow 不落盘，handoff §P-H.4）⇒ **配额值裁定与 brow 落盘是两件事**，不得用本条宣称桶化覆盖已完成。

## 四段退役路线 + 回滚预案

> 用户 2026-11-24 拍板：老端点读放大的止血**随 BR-①g 退役一并执行**；**只做「切读」就下老端点 = 不合格**。
> 本节把 D12 的五个阶段映射成「双写 → 校验 → 切读 → 退役」四段可执行流程。

### 四段流程与阶段映射

| 段 | 阶段 | 动作 | 老端点状态 | 进入下一段的**判据** |
|---|---|---|---|---|
| **① 双写** | 0 → **1** | 推拉**都双份**（老端点 + 桶端点） | 仍活跃 | ① 桶端点请求零 4xx/5xx；② 桶端点拉取的桶数 = 服务端 `sync_buckets` 该用户行数；③ 客户端侧车 `brow` 行数 = 已推成功桶数；④ 两路拉取的**条目集合逐条 HLC 一致**（允许桶端点多条目，不允许少） |
| **② 交叉校验** | **1 → 2** | 双写**继续**，叠加**交叉校验**：同一轮内对比老端点与桶端点拉到的条目内容/HLC | 仍活跃 | ① 连续 **N 轮（N ≥ 3）**交叉校验差异数 = **0**；② 差异 > 0 时**必须**有可定位的差异明细行（不是只报计数）；③ 该期间老端点侧**零意外写入放大**（`sync_items` 表写入增量 ≤ 真实变更条数） |
| **③ 切读** | **2 → 3** | **只拉桶、只推桶**，老端点**完全不发** | **停发但代码保留** | ① 连续 **N 轮**客户端诊断行证明**零**老端点请求；② 桶端点拉取**一轮扫完**（16 页内 `has_more=false`）；③ 稳态零写：连续 3 轮无指纹变化的桶**零推**；④ 跨设备可见性不回退（另一设备经桶端点能拉到同一集合） |
| **④ 老端点退役** | **3 → 4** | 老端点退役：服务端老端点下线、`sync_items` 表按另行 ADR 处理 | 下线 | ① 阶段 ③ 判据连续满足 **≥ 7 天**；② 生产 `sync_items` **零写入** ≥ 7 天；③ 回滚预案**已演练**（见下）；④ 服务端老端点下线**单独授权**执行 |

### 触发条件（任一命中 ⇒ 立即回退到上一阶段）

| 触发 | 判据 | 回退目标 |
|---|---|---|
| 桶端点错误率升高 | 连续 3 轮出现桶端点 4xx/5xx | 阶段 1（双写） |
| 交叉校验差异 | 差异明细非零且连续 2 轮无法定位 | 阶段 1 |
| 桶端点漏数据 | 桶端点拉取集合 ⊊ 老端点拉取集合（**任何一轮**） | 阶段 2（双写+校验） |
| 写放大回归 | `sync_buckets` 表写入增量 > 变更桶数 × 2（稳态轮） | 阶段 1 |
| 库存扫不完 | 16 页内 `has_more=true`（或总桶数 > 1600） | 阶段 1 |
| 预算护栏误伤 | 桶端点推触发 429 `write_budget_exceeded` 且非真实超额 | 阶段 1 |

### 回滚步骤（**回滚 = 把环境变量设为 0 跑一轮**）

```
1. 设 FLUXING_CLOUD_SYNC_BUCKET_PHASE=0（用户级环境变量）
2. 跑一轮同步（客户端下一次同步即生效；环境变量生效会写回侧车 phase=0）
3. 验证：诊断行显示本轮只走老端点；桶端点零请求
4. 云端桶数据**保留不动**（sync_buckets 行 + R2 桶对象不删）⇒ 可随时重新开阶段
```

- **回滚是配置级操作**：不改代码、不重装、不删云端数据、不回滚迁移。
- **回滚代价**：回到阶段 0 后桶化首导成果不再增量同步（老端点与桶端点数据分叉）；桶端点已推数据**留在云端**，可在重新开阶段后继续用。
- **回滚前提**：阶段 0–3 期间**老端点始终可用** ⇒ 这正是「退役」必须放在阶段 ④ 且需单独授权的原因。

### 每段的证据要求（进下一段前必须留档）

| 段 | 证据 |
|---|---|
| ① 双写 | 两路请求日志 + `sync_buckets` 行数 + 侧车 `brow` 行数三者对齐记录 |
| ② 交叉校验 | 连续 N 轮的交叉校验差异行（差异 = 0） |
| ③ 切读 | 连续 N 轮「零老端点请求」诊断行 + 一轮扫完记录 + 稳态零写记录 |
| ④ 退役 | ≥ 7 天零写入观测 + 回滚演练记录 + 用户授权记录 |

## 补推分批策略

### AC-112 四项数值（**每桶条目数取值 / 对应桶数 / 单轮预估传输时长 / 客户端单次超时窗口**）

| 项 | 取值 | 来源 | 状态 |
|---|---|---|---|
| **每桶条目数取值** | ≈ **92** 条（本地全集 94,604 ÷ 1024 桶）；未上云口径 53 条（54,536 ÷ 1024） | D15 / D23 拍板取值 | **已定** |
| **对应桶数** | **1024** / 词典 | `kBucketShardCount = 64` × `kBucketSubShardCount = 16` | **已定** |
| **单轮预估传输时长** | **未判定** | 需真实 R2 put 吞吐实测。**ADR 0077 D9 表格的 7.5 s 是「64 条/桶」的推算值，不是本粒度（≈92 条/桶）的实测值**，不可直接引用 | **未判定**（需要什么：真实词典的桶 blob 字节数抽样 + 生产 R2 put 吞吐实测） |
| **客户端单次超时窗口** | **30 s** | `WeaselServer/Cloud/CloudTransport.h` | **已定** |

> **未实测者不得写成已达成**：单轮预估传输时长**当前记「未判定」**。本批**不得**据 D9 的推算值宣称「已落在 30 s 窗口内」；真机判据见 spec 103 的 AC-203。

### 结论

**桶化后不需要分日 pacing。** 客户端侧只需要两层保护：**每请求 ≤ 64 桶**（D20）+ **失败续传**（没推成功的桶不写 `brow`，下一轮继续）。

### 数字

| 项 | 条目级（老端点） | 桶级（BR-①g） |
|---|---|---|
| 首导对象数 | 94,604 **条**（本地全集；其中未上云 54,536 条） | ≈ **1024 桶** |
| D1 行写入量 | ≈ 54,536 行（`sync_items`） | ≈ **1024 行**（`sync_buckets`） |
| 相对 10 万行/天额度 | **超限**（约 1.09 倍，单日打爆） | **约 2%**，安全 |
| 单请求对象数 | 64 条（`MAX_PUSH_ITEMS`） | **64 桶**（`MAX_PUSH_BUCKETS`） |
| 首导请求数 | ≈ 852 个请求 | ≈ **16 个请求** |
| 单轮拉取覆盖 | 1000 条 / 轮（`kPullPageLimit` × `kMaxPullPages`） | 100 × max(16, 词典数 × 11 + 2) 桶 / 轮（单词典 1600 ≥ 1024 ⇒ 一轮扫完；硬上限 32 页） |

### 为什么不需要分日 pacing

- **pacing 的存在理由是「单日额度不够」**（约 1.09 倍 > 1.0）。桶化后写入量降到约 2% ⇒ **前提消失** ⇒ pacing 变成纯延迟（把首导摊到多日 ⇒ 用户跨设备不同步窗口变长），是**净负收益**。
- **不推翻 BR-①e「维持现状」**：BR-①e 拍板针对的是**条目级**首导的 5.4 万条量级；桶化把该量级降到 1024 行 ⇒ 结论随之收敛，但**不修改 BR-①e 的历史结论**，只在本 ADR 记录前提变化。
- **失败续传替代 pacing**：桶级推失败的桶**不写 `brow`** ⇒ 下一轮自然重试 ⇒ 无需额外的「每日配额调度器」状态机，也无需跨日持久化进度。
- **仍保留的兜底**：服务端每账号每日桶行预算（`WRITE_BUDGET_BUCKETS_PER_DAY`，生产绑定 4000）继续在服务端侧兜底 ⇒ 客户端不需要自研 pacing。**每账号口径 ≠ 全局额度护盾**（ADR 0076 已知边界，BR-② 不立项）这一限制**不因桶化而消失**。

| STEP 4 部署 Worker | DONE | `DEPLOY_EXIT=0`；新生产 Version `4f163326-f2a5-4c69-be56-24cb800e6915`；D8 双口径绑定回读 `WRITE_BUDGET_ROWS_PER_DAY=80000` / `WRITE_BUDGET_BUCKETS_PER_DAY=4000` |
| STEP 5 桶端点生产冒烟 | DONE | **9/9 PASS**（HLC 守卫生效 + `cipher` 原样往返 + 跨设备可见 + 清理零残留） |
| STEP 6 BR-①g 客户端桶化 | **SKIP** | `BLOCKED_BY=STEP1`（AC-09 复跑判定 FAIL）⇒ 未改任何客户端代码 |

**客户端（BR-①g）尚未复验**：客户端桶化代码**尚未编译验证**（详见「客户端段（批次 BR-①g）」与 spec 103 的 tasks 状态行）⇒ 本节**不含**任何客户端侧生产数字。
