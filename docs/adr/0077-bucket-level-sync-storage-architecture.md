# ADR 0077: 云同步存储架构改桶级索引 —— D1 降为「设备 × 桶」双维索引，词条包落 R2

> 批次 BR-①f · 承接 [ADR 0076](0076-cloud-write-amplification-governance-and-zero-write-register.md) · 关联 spec `102-bucket-level-sync-storage`
> 取证报告：`reports/fluxing-br-1f/recon-blob-arch.md`（705 行，只读取证）

## Status

**Proposed**（2026-11-24：设计已定稿并落本 ADR；**服务端实现尚未完成**，老端点 `/v1/sync/push` `/v1/sync/pull` 保持原样不动，生产零风险）

本 ADR **不修改** ADR 0076 已采纳的决策（D1 失败注册零写入化 / D2-3 写预算护栏 / D2-4 `DELETE+INSERT` / D3 设备与令牌上限 / D4-* 失败重发）。
它只**扩展**护栏的计量对象（行 → 桶行），并**新增**一条并行协议路径。

---

## Context

### 0. 为什么现在必须改架构

【实测】2026-11-24 12:04（北京时间）生产 D1 读数：`rows_written_24h = 33,043`、`rows_read_24h = 9,083,789`、`write_queries_24h = 13,110`、`database_size = 19,255,296`、`num_tables = 8`。

【实测】D1 免费额度是**每数据库（全局）**、**按行写入**计、**UTC 日重置**、**硬失败**（`code 7500`）。一次全量首导 = 54,536 条 ⇒ 写放大后约 10.9 万行 ⇒ **一次首导即打爆单日 10 万行额度** ⇒ 该库内**所有**账号的所有写操作一起失效（含真实用户登录要写的 `refresh_tokens`）。

【实测】`rows_written_24h` 面板指标是**滚动 24h 窗口**，与 UTC 日不等价（12:04 读 33,043 vs 09:35 读 79,941 即证）。

【实测】`sync_items` 当前 40,061 行 ⇒ 一行一个词条 ⇒ **D1 行数 ≡ 词条数**。这是额度被烧穿的**唯一根因**：D1 被当成词条仓库用，而它每天只有 10 万行。

### 1. 写放大已修，但架构没变

ADR 0076 的 D2-5a-9（语义指纹）已修掉「每轮同一批词条被误判为本地改动 ⇒ 每轮重分配新 HLC ⇒ 每轮全量重写」的放大源。
但**架构层面的 1 : 1 关系仍在**：`sync_items` 一行 = 一个词条 ⇒ 只要用户新增 N 个词条，D1 就必须写 N 行（重推还要 ×2，因为 `DELETE+INSERT`）。

⇒ **稳态零写**成立（客户端不再每轮重推），但**首导 / 重建 / 换机**仍是 O(词条数) 行写入，**免费额度扛不住规模化首导**。

### 2. 免费额度口径（官方）

| 资源 | 免费额度 | 我们的用量级 |
|---|---|---|
| D1 行写入 | 10 万行 / 日（UTC 重置，硬失败） | 首导 10.9 万行 ⇒ **单次打爆** |
| D1 行读取 | 500 万行 / 日 | 9.08 万行/轮 × 约 100 轮/日 ⇒ **已超** |
| D1 存储 | 5 GB | 19 MB ⇒ 富余 |
| Workers Paid | $5/月 ⇒ 首 5000 万行/月（含），读 250 亿行/月（含） | 可覆盖，但**未拍板** |

【推断】D1 行写入是**唯一**硬瓶颈（读写比差 1000 倍）⇒ 改架构的**唯一必要目标**是**把 D1 行数与词条数解耦**。

### 3. 硬约束（不可协商）

1. **E2E 不变量**：服务端只见密文，不解密、不解析明文、不比较内容（ADR 0039 / 0076 I8）。
2. **条目级 AAD 不得改动**：`aad = item_key | type | hlc_ms | hlc_counter | device`（`include/FluxingCloudEnvelope.h`）。这是老密文可验证性的根基。
3. **条目级 HLC 必须保留**：客户端 `RemoteWins` 是**条目级**裁决（`CloudSyncService.cpp` 的 `RemoteWins`）⇒ 桶化后若丢掉逐条 HLC，回退/乒乓风险回归。
4. **无协议版本协商**：客户端与服务端**没有任何 version / capability 字段**（取证报告 §3.5）⇒ 灰度只能靠**独立 URL 路径**。
5. **`server_seq` 语义随索引行变化**：现在是 `sync_items.id`；改桶后是桶行 id ⇒ **编号空间变化** ⇒ 侧车游标必须重置。
6. **R2 单对象 put 慢**：ADR 0074 实测单条 put ≈ 626–706 ms，并发 6 ⇒ 64 条 ≈ 7.5 s。桶大小直接决定单轮传输时长。
7. **写预算护栏是每账号口径**，D1 免费额度是每数据库（全局）口径（ADR 0076 已如实登记）⇒ 桶化**不解决**全局口径问题，只是把单账号放大源降下来。

## Decision

### D1 —— 目标架构：D1 从「逐条索引」降为「设备 × 桶」双维索引，词条包落 R2

我们把「一个词条一行」改成「**一个（设备 × 桶）一行**」，桶内容作为一个密文 blob 整体落 R2：

```
D1  sync_buckets(id AUTOINCREMENT, user_id, device_id, bucket_key,
                 hlc_ms, hlc_counter, hlc_device,
                 r2_key, cipher_len, item_count, updated_at)
    UNIQUE(user_id, device_id, bucket_key)
    INDEX (user_id, id)
```

- **写入量**：首导 = 设备数 × 桶数 行（默认 1 设备 × 64 桶 ⇒ **128 行**，替代 54,536 行 ⇒ **约 425 倍改善**）；
  稳态每轮 = 变更桶数 × 2 行（`DELETE+INSERT`，沿用 ADR 0076 D2-4 的既有口径）。
- **D1 行数与词条数彻底解耦** ⇒ 达成「D1 写入 O(用户数)」的目标。
- **R2 对象数** = 设备数 × 桶数（桶内同 key 覆盖 ⇒ 存储不随轮次增长）。

### D2 —— 桶成员：固定子集，与内容无关

桶 = 「**词典名** + **条目哈希分片**」的固定子集：

```
bucket_key = MAC(enc_key, "bucket:" + dict_name + ":" + shard)      // 十六进制，与 item_key 同一套派生口径
shard      = sha256(item_key)[0] >> 2                                // 固定 64 个一级分片
```

- 桶成员**只由 item_key 决定**，与「内容变没变」无关 ⇒ **改一条词条只重写 1 个桶**（不重写整册）。
- `bucket_key` 是客户端用口令派生的 MAC ⇒ **服务端看不见词典名**（延续 ADR 0059 的不透明身份口径）。
- 分片数固定 64（可配）。桶内条目上限 **4096**；超限时客户端**降级到老端点逐条推**（老端点在灰度期常在）⇒ 不实现动态二级分片。
- 桶大小与 R2 吞吐的权衡见 D9。

### D3 —— 桶 blob 格式：既有条目级信封文本块直接串接，**不做桶级二次加密**

桶 blob = **N 个既有 8 行信封文本块直接串接**（`include/FluxingCloudEnvelope.h` 的 `SerializeEnvelope` 产物：首行 magic `v1`，其后 7 行 `name\tvalue` 制表符分隔，字段序 `item_key / type / hlc_ms / hlc_counter / device / nonce / cipher`，每块以 `\n` 结尾 ⇒ 串接后共 8N 行）。

- **零新增格式、零新增 AAD**：客户端拆包 = 按 8 行切块后逐块 `ParseEnvelope`；条目级 AEAD 的 AAD（`item_key | type | hlc_ms | hlc_counter | device`）**逐字不变** ⇒ **老密文在新协议里仍可逐条验证**。
- **服务端不解析 blob**（沿用 ADR 0076 I8「服务端不解析信封 8 行文本」的口径）⇒ 桶级 HLC 由**客户端**计算并随请求上报，服务端只存不校。
- **不引入桶级 nonce / 桶级 AAD** ⇒ 取证报告 §4.2 草案里的桶级 AEAD 被本决策**否决**（AAD 混用风险归零、收益为零）。
- 服务端只见密文 ⇒ E2E 不变量保持。

### D4 —— HLC 守卫双层：服务端桶级，客户端条目级

- **服务端权威** = 桶级 HLC（该桶内所有条目 HLC 的最大值，沿用 `compareHlc` 的同一套规则）。
  守卫：服务端已存桶级 HLC **≥** 客户端送上来的桶级 HLC ⇒ **整桶跳过**（不写 R2、不写 D1、不推进 `server_seq`）⇒ 保住「不写放大」这最后一道服务端防线。
- **条目级 HLC 保留在 blob 内** ⇒ 客户端 `RemoteWins` 逐条裁决能力**不变** ⇒ 取证报告 §6.3 风险 2 被消解。

### D5 —— 每设备独立视图：同桶不同设备互不覆盖

D1 行含 `device_id` ⇒ 设备 A 推的桶 X 与设备 B 推的桶 X 是**两行、两个 R2 对象**。

- 客户端拉取时拿到**所有设备**的桶视图，按**条目级 HLC** 合并 ⇒ **无 lost update**（A 不会盖掉 B 的桶）。
- 桶级守卫只在**同一设备的同一桶**上生效 ⇒ 单设备单进程 ⇒ 不会自相覆盖。
- 代价：D1 行数上界 = 设备数（ADR 0076 D3 限 32）× 桶数（64）= 2048 行/账号 ⇒ 可控且可诊断。

### D6 —— 灰度：独立 URL 路径，老端点原样不动

新增端点（服务端先上，老客户端不受影响）：

```
POST /v1/sync/buckets/push
GET  /v1/sync/buckets/pull
```

- `/v1/sync/push`、`/v1/sync/pull` **保持原语义、逐字不动** ⇒ 生产零风险；新客户端走新路径。
- 无版本协商 ⇒ 只能靠路径分流（取证报告 R5）。
- **`server_seq` 语义从「条目行 id」变为「桶行 id」** ⇒ 客户端侧车**必须升版为 v2 并强制重置 `seq = 0`**（否则老游标会被解释成另一个编号空间 ⇒ 漏拉或重拉全量）。

### D7 —— pull 响应契约：顶层三字段同名同义保留

```json
{
  "buckets": [
    { "bucket_key": "<hex>", "device_id": "<hex>", "hlc": {"ms":0,"counter":0,"device":""},
      "cipher": "<base64 桶 blob>", "item_count": 852, "server_seq": 12345 }
  ],
  "next_cursor": "<base64url(id)|null>",
  "has_more": false,
  "server_seq": 12345
}
```

- 顶层 `server_seq` / `next_cursor` / `has_more` **必须保留同名同义**（客户端 `ParsePullResponse` 依赖）。
- `limit` 语义从「条目数」变「**桶数**」（默认 50 / 上限 100，沿用现有常量口径）。

### D8 —— 写预算护栏口径换表

- `used` 的 COUNT 从 `sync_items` 换到 `sync_buckets`；`planned` 的估算对象从「条目数」变「桶数」（桶首次出现 1 行 / 已存在 2 行）。
- 口径注释（`src/sync.ts` 的护栏小节）**必须同步改写**，否则会继续对外宣称「80,000 行 ≈ 允许一次全量重推」。
- 环境变量保留旧名兼容，新增 `WRITE_BUDGET_BUCKETS_PER_DAY`；旧阈值在桶化后已属巨量，默认值需重估。

### D9 —— 桶大小是「D1 行数 ↔ R2 吞吐」的显式权衡

【实测】ADR 0074：R2 单条 put ≈ 626–706 ms，并发 6 ⇒ 吞吐约 8.6 条/s。

| 桶大小（条） | 首导 D1 行数（1 设备 × 54,536 条） | 稳态单桶 put 时长（并发 6） |
|---|---|---|
| 64 | 852 行（≈ 64×改善） | ≈ 7.5 s |
| 256 | 214 行（≈ 255×改善） | ≈ 30 s（超 WinHTTP 30 s 超时） |
| 512 | 108 行（≈ 505×改善） | ≈ 60 s（超） |

⇒ **默认桶大小取 64 条**（首导 852 行，稳态单桶 ≈ 7.5 s 在超时内）。
提高 R2 并发度可放宽该约束，但**并发度提升需先实测**（ADR 0074 的 6 是当时选值）⇒ 登记为后续批次候选。

### D10 —— healed 自愈的粒度风险（已知边界，不在本次解决）

桶化后 R2 对象缺失 ⇒ 自愈只能删**桶行** ⇒ 连带丢掉该设备该桶的全部条目（现状只丢一条）。
本批**接受**该风险（桶很小，损失面有限），并登记为 **BR-①g** 候选（blob 内保留条目级索引，或客户端做部分恢复）。

### D11 —— 实施分期

- **本批（BR-①f）= 服务端先行**：新表 + 新端点 + 护栏换表 + 单测 + 门禁 + 部署。
  老端点不动 ⇒ **生产零风险**，可独立验收。
- **下一批（BR-①g）= 客户端**：分桶打包 / 拆包、桶级 HLC 分配、侧车 v2 升版与 `seq` 重置、分页预算第二道闸、打包装机 + 真机判据。
- `sync_items` 表与老端点的**退役**另立 ADR（条件：客户端全面切新端点且 AC-09 连续稳定）。

### 备选方案与否决理由

| 备选 | 否决理由 |
|---|---|
| **直接升级 Workers Paid** | 不改放大源，只是把阈值抬高；D1 行数仍 ≡ 词条数，规模上去后再次打穿；且**用户未拍板**。 |
| **分日 pacing（把首导切成 N 天）** | 首导窗口变成 N 天，用户数据在此期间跨设备不同步；且需要引入调度状态机。BR-①e 已拍板「维持现状」，本 ADR 不推翻。 |
| **每设备一个全量 blob（D1 1 行/账号）** | D1 行数最优，但**稳态每次改一条就要重传全量词典**（10~40 MB），出网流量与 30 s 超时都扛不住；桶化把这个代价限制在 1 个桶内。 |
| **桶级二次 AEAD（桶 nonce + 桶 AAD）** | 引入第二套 AAD ⇒ 混用风险与老密文验证问题；条目级 GCM tag 已提供逐条完整性 ⇒ 收益为零、风险为正。 |
| **服务端在密文域做桶内合并 / 去重** | 服务端无密钥，AAD 含 hlc 且 nonce 随机 ⇒ 密文域无法去重（ADR 0076 D2-2 已关闭该路线）。 |

## Consequences

### ✅ 变得更容易

- D1 行写入与词条数**解耦** ⇒ 首导从 ~10.9 万行降到 852 行量级 ⇒ 免费额度从「单次打爆」变为「可支撑规模化首导」。
- 稳态每轮 D1 写 = 变更桶数 × 2 行 ⇒ 接近 0。
- 服务端只见密文、条目级 AAD 不变 ⇒ E2E 语义零变化，无需重新设计密钥体系。

### ⚠️ 变得更难

- **客户端要实现桶打包 / 拆包 + 桶级 HLC 分配 + 侧车 v2 升版**（下一批 BR-①g）。
- **首导传输仍是全量词典**（密文不可压缩）⇒ 家宽上行 10 Mbps 下 40 MB ≈ 32 s ⇒ 必须分批 + 后台完成，客户端 30 s 超时（`CloudTransport.h`）需要按批次规避。
- **R2 put 吞吐成为新瓶颈**（D9）⇒ 桶大小与并发度成为需要实测的参数，不是自由选择。
- **healed 自愈粒度变粗**（D10，BR-①g 候选）。
- **出网流量**成为次级瓶颈（免费 100 GB/日 ⇒ 约 26 个活跃全量同步用户/日）⇒ 桶化把流量从「稳态每轮全量」降为「稳态每轮 1 桶」，但首导仍是全量。

### 🔒 新增约束

- 任何对桶 blob 格式的改动都是**协议级**改动 ⇒ 必须**同时**改服务端 + 客户端 + 两侧单测，且必须走 ADR。
- 桶级 HLC 与条目级 HLC **必须同时存在**；只留其一 ⇒ 必然回退或乒乓。
- `server_seq` 编号空间在两套端点间**不同** ⇒ 侧车必须按协议版本分区，**禁止**跨版本复用游标。

### 🔁 可逆性

**部分可逆**：新端点与新表是**增量**的，老端点与 `sync_items` 保持原样 ⇒ 客户端出问题时可立即切回老端点（客户端侧开关）。
`sync_buckets` 表可 `DROP TABLE` 回滚。**不可逆的部分**：一旦客户端写入桶级数据，`sync_items` 的历史行**不能自动迁回** ⇒ 退役必须走「双写 → 校验 → 切读 → 退役」的显式流程。

## 与既有决策的关系

| 既有决策 | 关系 |
|---|---|
| ADR 0039（E2E + 合并落客户端） | **继承**：服务端只见密文、合并落客户端不变。 |
| ADR 0059（item_key 不透明 MAC 身份） | **继承并扩展**：桶键沿用同一套 MAC 派生口径。 |
| ADR 0073 / 0074（推送批量与吞吐） | **继承**：分批与并发化机制沿用；`MAX_PUSH_ITEMS` 语义在桶化端点另定（D8）。 |
| ADR 0076 D2-3（写预算护栏） | **扩展**：计量对象从「行」变「桶行」，阈值语义与注释同步改写（D8）。 |
| ADR 0076 D2-4（`DELETE+INSERT`） | **继承**：桶行同样用 `DELETE+INSERT` 拿新 id。 |
| ADR 0076 D3（设备上限 32） | **继承**：D1 行数上界 = 设备数 × 桶数（D5）。 |
