## 1. 背景与问题

### 1.1 现状写序

两条推送路径的写序完全同构，且都是**跨两个存储的两次独立提交**：

| 步骤 | 条目级 | 桶级 |
| --- | --- | --- |
| ① 预算护栏（任何写之前） | `sync.ts:315-329` | `sync-buckets.ts:225-232` |
| ② 算 R2 key | `sync.ts:331-336` | `sync-buckets.ts:236-239` |
| ③ 写 R2（并发 6，同 key 覆盖） | `sync.ts:340-357` | `sync-buckets.ts:240-258` |
| ④ 写 D1：`DELETE` + `INSERT` 组 batch | `sync.ts:359-391` | `sync-buckets.ts:260+` |
| ⑤ 回读 `MAX(id)` 取 `server_seq` | `sync.ts:393-412` | 同构 |

R2 与 D1 **没有共同事务**（R2 不是事务型存储，D1 `batch` 也不是 R2 的一部分）。
写序是「R2 先、D1 后」，所以失败只能落在两处。

### 1.2 当前实现下，D1 失败会造成什么

设条目 K 已在云端（HLC₁ / nonce₁ / cipher₁ / `r2_key₁`），客户端用 HLC₂ / nonce₂ / cipher₂ 重推：

1. ③ 成功：`r2_key₁` 这个**同一个 key** 被覆盖成 cipher₂（含新的 `customMetadata.hlc_ms/hlc_counter/nonce_b64`）；
2. ④ 失败：D1 行仍是 HLC₁ / nonce₁ / `cipher_len₁` / `r2_key₁`。

结果是**同一行索引与对象内容跨版本混搭**。它不是「短暂不一致」，而是**读者可见的确定性故障**：

| 读者拿到的 | 后果 |
| --- | --- |
| `nonce₁` + cipher₂ | **解密失败**（cipher₂ 是用 nonce₂ 加密的）⇒ 客户端报错、该条目本轮同步失败 |
| HLC₁ + cipher₂ | 客户端按 HLC 判「无变化」⇒ 若它先落了 HLC₁，则永远不会重拉这条 ⇒ **静默丢更新** |
| `cipher_len₁` + cipher₂ | 只打一条 `console.warn`（`sync.ts:456-460` / `sync-buckets.ts:374-378`）⇒ **不拦截** |

桶级同构且更重：一个桶 = 最多 N 条条目的 blob，`sync-buckets.ts:366-372` 的注释已经点明
「桶化后这里是丢一整桶条目而非丢一条」。

### 1.3 三个候选

| 候选 | 做法 | 否决/采纳理由 |
| --- | --- | --- |
| **A 延迟提交** | 先在 R2 写临时 key，D1 提交成功后再「提升」成正式 key | R2 没有原子 rename ⇒ 「提升」本身是第二次写，失败窗口只是搬了个位置；且读路径要认两种 key，复杂度上升 |
| **B 版本化 key** | 每次写入落到**新 key**，D1 行指针整体指向新 key，提交成功后再删旧对象 | 让「对象覆盖」这件事**不再发生** ⇒ 索引与对象之间从「覆盖关系」变成「指针关系」，混搭在结构上不可能 |
| **C 失败回写旧对象** | 捕获 D1 失败，把 cipher₁ 写回 `r2_key₁` | 回写本身也会失败（同一个 R2）；且要回写就必须先留住 cipher₁ ⇒ 等于自建一层影子存储，复杂度超过收益 |

**选 B。**

### 1.4 为什么不选「什么都不做」

`sync.ts` 的自愈逻辑（`sync.ts:449-454`）与桶侧（`sync-buckets.ts:366-372`）在
「对象不存在」时**删掉索引行**。这条自愈在覆盖语义下是安全的；但在版本化语义下它会变成
**误杀**的通道：任何让「指针指向的对象被删」的路径（含误删、误 GC、运维手滑）都会让云端
静默丢一条/一整桶。因此本 ADR 同时收紧 GC 的删除判据（D6 / D10），这是 B 方案能成立的**配套条件**，不是可选项。

## 2. 决策

### D1 · key 形态：确定性版本后缀，同层不进子目录

| 路径 | 现状 | 版本化后 |
| --- | --- | --- |
| 条目级 | `u/<uid>/<sha256(item_key)>`（`wire.ts:214-216`） | `u/<uid>/<sha256(item_key)>.<hlc_ms>-<hlc_counter>-<dev12>` |
| 桶级 | `b/<uid>/<sha256(device_id)>/<sha256(bucket_key)>`（`wire.ts:329-336`） | 同左，末段后接 `.<hlc_ms>-<hlc_counter>-<dev12>` |

- `dev12` = `sha256Hex(utf8(hlc.device))` 的前 12 个十六进制字符。
  **必须含设备维度**：条目级 key 不含设备（`u/` 是跨设备单视图），若版本号只取 `ms-counter`，
  设备 A 与设备 B 在同一毫秒同一计数器上推同一条目就会撞出同一个 key ⇒ 退化成覆盖语义，
  U1 问题原地复活。桶级 key 本已含 `deviceHash`，此处的 `dev12` 只是保持两条路径的版本号同构。
- 版本号必须是 **(ms, counter, device) 的纯函数**，不得取随机数、`Date.now()`、单调计数器或 UUID——
  见 D4 的幂等论证。
- **用点号接在同层，不用子目录**：本地 fs 底座（`pg/r2-fs.ts`）把 `/` 映射成目录层级。
  `u/<uid>/<hash>/<ver>` 会为 40 069 个条目各建一个目录（inode 放大、`list` 变慢）；
  `u/<uid>/<hash>.<ver>` 仍是单层文件。`encodeSegment`（`r2-fs.ts:81-89`）只转义**段尾**的点
  （`a.` → `a%2E`）与段首下划线、Windows 保留设备名；`<hash>.<ver>` 的点不在段尾，编码可逆，
  与 `decodeObjectKey`（`r2-fs.ts:124-126`）往返无歧义。
- 长度：条目 key 由 103 → **约 138** 字符；桶 key 由 168 → **约 203** 字符。
  `r2_key` 列在两侧底座都是 `TEXT`（`migrations/0001_init.sql:65`、`migrations/0004_sync_buckets.sql:41`、
  `migrations-pg/0001_init.sql:123` 与 `:192`），无长度上限，**不需要迁移 DDL**。

### D2 · 写序：五步，删除在提交**之后**

```
① 预算护栏（不变，仍在任何写之前）
② 算新 key（纯函数）
③ put R2 新对象（新 key，不覆盖任何已有对象）
④ D1 batch：DELETE + INSERT，行内 r2_key = 新 key          ← 提交点
⑤ 提交成功后：delete(旧 r2_key)，仅当旧 key 存在且 ≠ 新 key
```

不变式：**③ 与 ⑤ 之间，任何崩溃都只留下一个没人引用的对象**；`④` 失败时不执行 ⑤ ⇒
旧对象仍在、旧指针仍指向它 ⇒ 读路径拿到的仍是**完整且自洽**的旧版本。

### D3 · 删除的触发条件（三条同时成立才删）

1. `④` 的 batch **返回成功**（抛错不删）；
2. 该行**变更前**的 `r2_key` 存在（新条目/首次推送没有旧对象，跳过）；
3. 旧 `r2_key` **不等于**新 key（同版本重推时二者相等，删了就会删掉刚写的对象——这是本设计里唯一能造成数据丢失的写法，必须显式排除）。

删除形态：单批一次 `delete(keys: string[])`（`account.ts:41` 已在用数组删除；`FsBucket` 与 R2 均支持），
每批最多 64 个旧 key ⇒ **每批 R2 请求数 +1**，不改变 ADR 0074 关于「写阶段并发 6 与 15 s 客户端超时」的结论。
删除失败**不得**让整批报错（提交已经成功，业务语义已完成）：只记一条
`[fluxing-sync] orphan object left key=<key>` 日志并继续返回成功。

### D4 · 幂等语义：从「无条件幂等」降为「条件幂等」，且降级只花空间

- 同一次逻辑推送的**重试**（客户端原样重发同一请求体）⇒ `(ms, counter, device)` 不变 ⇒ 新 key 不变 ⇒
  落到同一个对象上，与现状的「同 key 覆盖」等价。
- 若重试时客户端已经推进了 HLC（重新走了一轮生成）⇒ 新 key 与上一次不同 ⇒ 桶里多一个对象，
  但 D1 只有一行、指针指向最后成功的那次 ⇒ **数据仍然一致**。
- 因此本方案把「一致性风险」结构性降级为「空间债」，而空间债可由 D3 的同步删除与 D6 的兜底 GC 回收。

### D5 · D1 失败时不尝试补偿

不写「失败回写旧对象」（候选 C）。理由：回写需要旧内容在手，而旧内容只在 R2 里、已被 ③ 之外
的路径改过就不再是旧内容；为它建影子副本等于自建第二个存储。**接受「多一个孤儿对象」作为唯一补偿**。

### D6 · 孤儿兜底 GC：工具化，不自动

- 主路径删除（D3）是唯一**自动**的清理动作。
- 兜底清理提供显式工具：按用户、**默认 dry-run**，列出候选并打印判据，`--apply` 才删。
- 候选判据**只能来自 D1 指针**：解析对象 key 的 `<hash>` 段 → 查 `sync_items` / `sync_buckets` 中该
  `user_id` 的 `r2_key` 集合 → 不在集合内且 `age > 7 天` 才是候选。**禁止**只凭文件名模式
  （「带版本后缀就是旧的」）判定——旧的无版本对象的 key 也符合某条正则时会被误删。
- **周期性自动 GC 不在本 ADR 范围**：误删 = 数据丢失，且会经由 1.4 的自愈变成「静默删行」。
  要自动化需独立批次 + ADR + 必红阳性对照的验收（先证明「保护当前指针」这条判据有鉴别力）。
- 现有登记「R2 孤儿无害」（handoff `:92`）继续成立：孤儿不参与任何读路径，只占空间；
  前缀 clear（D7）能一并清掉。

### D7 · 读路径与前缀清理：零改动

- 拉取（`sync.ts:430-439` 的 SELECT 含 `r2_key`，`sync.ts:448` 用 `env.BUCKET.get(row.r2_key)`；
  桶侧 `sync-buckets.ts:346-356` / `:365`）**从不按规则拼 key**，只用行内指针 ⇒ key 变形对读路径透明。
- `account.ts` 的 clear 按前缀 `u/<uid>/`（`:85`）与 `b/<uid>/`（`:86`）整体清，版本化不改变前缀，
  多版本对象都在前缀内 ⇒ `clearPrefix`（`:53-79`）的「清完自证」不变量（`:73-76`）继续成立。
  轮次上限 `MAX_ROUNDS=1000` × `LIST_LIMIT=1000` = 100 万对象，远大于最坏 2 倍膨胀后的对象数。
- 因此 `deleted_objects` 的口径自动扩为「含版本残留的对象总数」，**字段名与类型不变**。

### D8 · 混合态合法，且自动收敛

生产存量（条目 40 069 / 桶 1 000）全部是**无版本旧 key**。本 ADR **不迁移历史对象**、不改历史行的 `r2_key`
（红线：不清洗、不重建用户数据）。混合态的合法性来自 D7：旧行指针仍然有效、仍可读。
收敛性来自 D3：任何条目/桶下一次被成功推送时，自动升级为版本化 key，旧对象在提交成功后删除。
所以「从未被再推送过的对象」会永久保持旧形态——这是**允许的终态**，不是待办。

### D9 · 不改变的上游决策

- ADR 0074：R2 写并发 `R2_WRITE_CONCURRENCY = 6`、按波推进、「R2 先 D1 后」（`r2-write.ts:15`、`:57-69`）。
  本 ADR 只**新增**一个删除步骤（D3），不改动 put 的并发与波的语义。
- ADR 0076 D2-3：写预算护栏仍在**任何写动作之前**判定（`sync.ts:315-329`、`sync-buckets.ts:225-232`）⇒
  超限时 R2 与 D1 双零写入，本 ADR 不放宽。
- ADR 0077：桶 key 的设备维度、桶 blob 的服务端零解析、老端点语义逐字不动。
- ADR 0079 D8 三条硬闸门（假空 / 数据核对 / 回滚）一条都不解除。

### D10 · 自愈语义随之收紧

`object === null` 时的「删索引行 + 告警」（`sync.ts:449-454`、`sync-buckets.ts:366-372`）保留为最后手段，
但本 ADR 追加两条约束：

1. 正常路径下它**不应被触发**：版本化后，指针指向的对象只在「提交成功后删旧」里被删，而那时指针已前进。
   任何一次触发都说明有本 ADR 之外的删除源（误 GC / 手工清理 / 存储丢对象）⇒ 日志必须能区分
   （现有 `console.warn` 已带 `r2_key` 与条数，够用，不新增格式）。
2. GC（D6）的判据必须**显式排除当前指针**，且必须有必红阳性对照：构造一个「当前指针指向的对象」作为
   负样本，GC 若删它即判定失败。

## 3. 不变量（可测清单）

| 编号 | 不变量 | 检测方式 |
| --- | --- | --- |
| I1 | D1 行的 `r2_key` 在同一行内**整体**指向一个版本；不存在「索引旧、对象新」的混搭 | 单测：mock R2 记录 put 序列，mock D1 让 batch 抛错，断言 R2 上不存在「被覆盖的旧 key」 |
| I2 | batch 失败时**不执行**删除 | 单测：断言 delete 调用次数为 0 |
| I3 | 旧 key == 新 key 时**不删除** | 单测：同 (ms,counter,device) 重推，断言对象仍在 |
| I4 | 删除失败不影响返回成功 | 单测：delete 抛错，断言 handler 仍返回 `server_seq` |
| I5 | 版本号是纯函数 | 单测：同输入两次调用逐字相等；不同 device / ms / counter 必不同 |
| I6 | 预算超限时零写入（R2 put 与 delete 均为 0） | 现有护栏测试扩一条断言 |
| I7 | 前缀 clear 能清掉多版本对象 | PG 侧集成测试：同一条目写两版后 clear，断言前缀为空 |
| I8 | 桶 key 的设备维度不被版本号破坏 | 单测：两设备同桶 key 前缀不同、版本号可独立变化 |

## 4. 失败矩阵（版本化后）

| 失败点 | 云端状态 | 读者可见后果 | 恢复动作 |
| --- | --- | --- | --- |
| ③ 中途失败（部分波已落盘） | 新对象部分存在、D1 未动 | 无（无人引用这些新 key） | 客户端重试；旧版本仍完整可读 |
| ④ batch 失败 | 新对象全在、D1 指向旧版本 | 无（读到完整旧版本） | 重试；孤儿由 D6 回收 |
| ④ 成功、⑤ 前崩溃 | D1 指向新版本、旧对象残留 | 无 | 孤儿由 D6 回收 |
| ⑤ 删除失败 | 同上 | 无 | 日志 + 孤儿由 D6 回收 |
| 进程在 ④ 内部中断（D1 batch 非真事务，见 §1.1） | D1 可能半批可见（D1 自身语义，非本 ADR 引入） | 与本 ADR 无关；**PG 侧 batch 是真事务**，切源后自然消失 | — |
| 运维误删当前对象 | 行指向缺失对象 | 自愈删行 ⇒ 丢一条/一桶（ADR 0077 D10 已知边界） | D10 约束：GC 必须有必红阳性对照 |

对照：**现状**下 ④ 失败即可产生 §1.2 的三种读者可见故障，且无日志能事后判定（只有 `cipher_len` 不一致时的 warn）。

## 5. 兼容与迁移

- **零数据迁移**：不改任何存量行的 `r2_key`，不重命名任何存量对象，不新增 DDL（`r2_key` 已是 `TEXT`）。
- **零读路径改动**：D7。
- **切换即生效**：本 ADR 落码后，下一次成功推送自动使用版本化 key；未再被推送的对象保持旧形态（D8）。
- **回滚**：把 `r2-write` 的新增删除步骤与 key 生成回退到 HEAD 即可。已产生的版本化对象仍可被旧代码读，
  因为读路径只用指针 ⇒ **回滚不需要数据清理**。这是本方案相对「延迟提交」的额外优势。

## 7. 非目标（明确不做）

1. 不做 R2 事务化 / 两阶段提交 / R2 与 D1 的分布式事务。
2. 不做周期性自动 GC（D6）。
3. 不迁移历史对象 key（D8），不重建、不清洗任何用户数据。
4. 不改 `account.ts` 的 clear 语义、字段名与「清完自证」。
5. 不改桶化阶段：`FLUXING_CLOUD_SYNC_BUCKET_PHASE` 恒 0，阶段 3/4 永久禁用。
6. 不改 `AC-09` 判定（仍 FAIL）、不复活 `AC-213/214`、不判定 `AC-212`/`AC-215②`。
7. 不在本 ADR 内修「规则 1 盲区」（`inventory_complete` 只看拉到底、`unproven_keys` 不收远端桶读不出的键）——
   它是逻辑漏洞、与底座无关，需独立批次 + ADR。

## 8. 后果

**正面**

- 「索引与对象跨版本混搭」在结构上不可能发生（只有指针整体更新）⇒ §1.2 的三种故障路径消失。
- 崩溃/失败一律收敛为「多一个无人引用的对象」，可观测、可回收、不影响读。
- 回滚不需要数据清理。
- 与本地 fs 底座兼容（单层文件、原子 rename 能力未被用到也不冲突）。

**代价**

- 对象数最坏 2 倍（正常路径下瞬时 2 个、稳态 1 个）。
- 每批 R2 请求 +1（一次批量 delete）。
- key 变长（约 +35 字符），运维读日志时需知道版本后缀的含义。
- 引入「幂等是条件性的」这一认知负担（D4）——必须在代码注释里写清，否则后来者会以为「重发一定不产生新对象」。

**风险与缓解**

| 风险 | 缓解 |
| --- | --- |
| 旧 key == 新 key 时误删刚写的对象 | D3 第 3 条 + I3 单测 |
| GC 误删当前指针 ⇒ 自愈静默删行 | D6 判据只认 D1 指针 + D10 必红阳性对照；自动化前必须另立 ADR |
| 后来者把版本号改成随机/时间戳 | D1 明文禁止 + I5 纯函数断言 |
| 桶级忘记同步改 ⇒ 两条路径语义分叉 | I8 + 桶侧独立用例（`sync-buckets.ts:236-258`） |
