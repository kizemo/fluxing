# 0055. 同步引擎：事件唤醒调度 + 服务端 HLC 守卫收敛，sidecar 是「已同步」的唯一真相源

## Context

阶段 D 交付的同步能力只有「一次性编排」：`CloudSyncCoordinator::SyncOnce()` 推一批、拉一批、合并、回写。阶段 F 要把它变成**长期运行的同步**，于是同时冒出四类问题：

1. **什么时候同步**：`plan.md` §7 的触发矩阵（启动拉一次 / 本地改动防抖推 / 每 60 分钟定时拉 / 手动立即同步 / 失败退避重试 / 每日配额）是纯调度问题，但宪法 P2 明令「TSF 回调与 UI 线程禁阻塞 I/O」，网络轮次只能落在后台线程。
2. **两端怎么收敛**：T102 的结论是「逐条目按 HLC 大者胜」，但只**合并到本地**是不够的 —— 两端同时改不同条目时，胜出的那条必须**同时存在于两端**，否则各拉一次就又分叉。
3. **不要写放大、不要乒乓**：若客户端把「远端来的条目」也回推，服务端版本会被推回旧值；两端各拉各推 ⇒ 条目在两端之间反复翻转。
4. **不要把配额打穿**：每日推 100 / 拉 50 是硬上限。原实现里顶层 `server_seq` 缺失时会被无条件写成 0 ⇒ 游标永不前进 ⇒ 每轮重复拉同一批 ⇒ **光重拉就吃光拉配额**。

此外有一条贯穿本阶段的硬约束：**未登录时零出向请求**（R9 / AC-12），以及「客户端与服务端各自维护 HLC 比较语义，必须逐字一致」。

## Decision

1. **引擎与凭据彻底解耦。** `CloudSyncEngine` 不持有 token / enc_key / 端点，只接受一个注入的 `SyncRunner` 回调（`std::function<bool(SyncDirection, CloudSyncRoundResult*)>`）。因此引擎可以脱离账号状态与网络单测（宪法 R7：生产与测试同源，纯函数内联在头文件里，测试不复制第二份实现）。**未登录就不启动引擎** ⇒ 「零出向请求」由构造方式保证，而不是靠运行时判断。

2. **调度用单调钟，显示与配额用墙钟。** 所有 deadline 用 `steady_clock` 计算（免疫墙钟跳变 / 夏令时），只有状态显示与「UTC 自然日翻篇」用墙钟。等待方式是 `cv.wait_until(deadline, pred{!running_ || wakeup_})` ⇒ **事件唤醒 + 定时唤醒，无轮询**。失败退避用阶梯 1 / 5 / 15 / 60 分钟，最多 4 次；用尽后交回定时触发（并把防抖窗口重新起算，避免立刻再撞一次失败）。

3. **触发优先级固定为：手动 > 退避重试 > 启动 > 本地改动推送 > 定时。** 手动同步**不受每日配额限制**（用户显式发起不该被配额挡）；配额用尽 ⇒ 结果是 `kSkipped`（**不是错误**），等 UTC 日翻篇重置。

4. **方向策略：启动轮只拉不推，其余轮次一律「推 + 拉」。**
   - 启动轮只拉（`plan.md` §7「启动 → 拉一次」，不阻塞启动、失败静默）；
   - 其余轮次推拉同做，因为**推送集合是 sidecar 差分算出来的**：只有「本地改动过」的条目才进集合，没有本地改动时**根本不发出推送请求** ⇒ 不写放大；
   - 若定时轮只拉不推，本地新增 / 修改的词条永远传不上云端 —— 差分能发现改动，但没人触发推送。60 分钟定时轮是「本地改动钩子缺失」时的兜底。

5. **收敛靠双保险，缺一不可。**
   - **服务端 HLC 守卫**（`cloud/fluxing-sync/src/sync.ts`）：push 的每条入参若 HLC **≤** 已存版本 ⇒ 整条**跳过**（不写 R2、不写 D1、不推进 `server_seq`），进响应的 `skipped` 数组；HLC 严格大于才接受。服务端比较规则（`ms → counter → device`，device 按 **UTF-8 字节序**而非 JS 的 UTF-16 码元序）与客户端 `CompareHlc` 逐字一致。
   - **客户端只推「本地改动过、且合并后仍是本地版本」的条目**：远端胜出的条目不回推（服务端已经握着它）。

6. **sidecar 是「已同步」的唯一真相源。** sidecar 每行 = 条目键 + HLC + 载荷 sha256。只有两种情况把条目标记成「已同步」：**远端胜出**（服务端已经握着它），或**本轮真的推送成功**。
   > ★ 只拉不推的轮次（启动轮）里，本地改动从未上传，此时**绝不能**标记成「已同步」—— 否则这条改动永远再也推不上去。原实现用 `locally_modified` 判定，会在启动轮误标；现改为记录 `pushed[]`（本轮实际推成功的条目）判定。

7. **分批与游标。** 推 200 条 / 请求；拉 100 条 / 页 × 最多 10 页 / 轮；超出部分下一轮继续，状态消息明示「云端还有更多条目，下次同步继续」。游标**只增不减**：顶层 `server_seq` 缺失时保留调用方传入值（不再写 0），条目自带的 `server_seq` 取 max 参与推进；游标一轮没前进就停手（防死循环刷配额）。

8. **服务端 pull 的顶层 `server_seq` 语义 = 「本次实际交付的最后一条条目的序号」**，不是「该用户的全局最大 id」。否则客户端游标会越过尚未交付的条目，造成**永久漏拉**。客户端侧另有一层保险：推进游标时取「顶层值与逐条 `server_seq` 的 max」，且顶层字段缺失时保留旧值。

9. **重发验证码独立成端点** `POST /v1/auth/resend`（`cloud/fluxing-sync/src/auth.ts` `handleResend`）：404 `email_not_found` / 409 `email_already_verified` / 429 `verify_too_frequent`（60 秒频率闸）/ 200。客户端 `CloudAccountService::ResendVerification` 不改状态机（重发不落凭据、不改登录态）。

## Consequences

- ✅ **引擎可单测**：不碰网络、不碰凭据，纯函数内联在头文件里，与生产同源。
- ✅ **未登录零出向**：引擎在无凭据时压根不启动。
- ✅ **无写放大、无乒乓**：推送集合按差分裁剪 + 服务端 HLC 守卫兜底。
- ✅ **配额可控**：游标只增不减 ⇒ 不再出现「每轮重拉同一批」的打穿。
- ✅ **失败不打扰用户**：退避静默、不弹窗、不阻塞输入（宪法 P2）。
- ⚠️ **本地改动的「即时推送」钩子本批未接**：rime 的提交事件发生在 TSF 客户端进程，接入它需要新增一条 IPC 消息 ⇒ 触发 CLAUDE.md 的「IPC 四边同步」红线（server / TSF / deployer + ADR + 测试）。当前由 60 分钟定时轮兜底传播，代价是本地改动最长延迟一小时。
- ⚠️ **客户端不解析 `skipped`**：服务端跳过信息对客户端是惰性的（不影响收敛，因为服务端已阻止回退）。若将来要区分「本次真正被接受的条目」，需客户端批次补解析。
- ⚠️ **`restore_user_dict` 是合并语义**（`abs(commits)` 择优、dee 取 max、tick 抬升）：合并快照未必能覆盖掉本地胜出的冲突条目 ⇒ 端到端收敛（AC-08 / AC-09）仍须真机双机验证，不能由单测宣称。
- ⚠️ **sidecar 路径是窄串**（协调器内部用窄路径 API）：当前落点 `D:\Program Files\fluxing\user1\fluxing` 是 ASCII，安全；若将来用户数据目录含非 ASCII 字符，需把协调器改成宽路径。
- ➕ **服务端响应形状是加性的**：`push` 响应新增 `skipped`、`pull` 响应新增顶层 `server_seq`、`auth` 新增 `/v1/auth/resend` —— 旧客户端忽略新字段仍可工作。
- ➕ **可回退**：客户端「只推变化条目」与「服务端 HLC 守卫」互为备份；任一侧回退，另一侧仍能挡住版本回退。
