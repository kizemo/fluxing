# ADR 0028 — 薄 TSF 壳、IPC 协议只增不改、锁定降级用每次安装唯一文件名

- **Status**: Accepted
- **Date**: 2026-11-01
- **Spec**: [097-shim-name-collision-and-hotkey-chord-separation](../../.specify/specs/097-shim-name-collision-and-hotkey-chord-separation/spec.md)
- **Lessons**: L164、L165
- **Supersedes / superseded by**: —（新增）

---

## 背景

三件互相纠缠的事撞在了一起。

**第一件：更新输入法的模块文件时要求重启系统。**

输入法在 32 位与 64 位宿主进程里各加载一份模块文件。更新安装时，如果该文件正被某个宿主进程映射，普通的覆盖写入会失败。旧的处理办法是：改用一个带版本号的新文件名落地，把系统注册指向它，如果连改名都失败就写一个「等重启再换」的标记。

但那个带版本号的名字只由版本号和构建号决定，**没有每次安装唯一的分量**。于是第二次同版本覆盖安装时，这个名字已经被上一次的副本占着、而且正被映射 ⇒ 删除静默失败 ⇒ 新文件写不进去 ⇒ 又退回「等重启再换」。用户每装一次就被迫重启一次，而系统看起来一切正常，没有任何报错。

**第二件：TSF 壳已经薄到极限，但还差最后一层。**

输入法的 TSF 前端其实已经是一个薄壳：它只引用通信层与界面层，不链接词库引擎、不链接业务层。但有一类东西天生搬不走 —— 宿主进程内才能拿到的原始按键、扫描码、按键状态与焦点上下文，以及 COM 生命周期本身。

于是有人会问：能不能干脆让 TSF 壳变成一个「永不改名的固定入口」，把实现挪到后面去，从而彻底摆脱文件被占用的问题？

**第三件：权威安装门禁自己在腐化，而且不报错。**

两个门禁脚本用四段式的正则挑待验安装包，而构建产物早就改成了三段式版本名（第四段只进内部资源与版本化文件名）。一个都匹配不上 ⇒ 门禁静默判失败退出 ⇒ 门禁自三段式启用以来从未真正验过任何一个包。另一处：新增断言的编号与另一阶段已占用的编号重叠，机器可读报告里会出现重复键。

---

## 决策

### 决策 1 — 薄 TSF 壳是硬性设计准则，不是现状描述

TSF 前端**只**允许依赖两样东西：通信层（与后台服务之间的管道协议）与界面层（候选窗渲染）。它**不允许**：

- 链接词库引擎；
- 链接业务层；
- 直接读用户数据目录；
- 在输入法回调内做阻塞式文件 I/O、同步注册表访问、等待信号量。

任何「前台需要知道的东西」都必须由后台服务通过通信管道推给前台，前台不得自己去找。

**留在壳里的白名单只有四类**，且必须逐条说明为什么搬不走：

1. TSF 的 COM 生命周期（类工厂、配置文件切换通知）；
2. 候选窗渲染（界面层静态链接进壳）；
3. 宿主进程内才有的原始按键 / 扫描码 / 按键状态；
4. 宿主进程的焦点上下文。

**评审门槛**：任何让壳变厚的改动，必须在本 ADR 的「白名单」里找到对应条目，否则不予通过。

### 决策 2 — 通信协议只增不改

现有通信协议**没有版本号、没有魔数、没有握手**，只有一张焦点标志协议表。因此：

- 新增字段**只能追加**，且新字段的语义必须是「老端忽略也不出错」；
- 改变已有字段的含义、改变命令号的语义、复用已废弃的字段，一律禁止；
- 新增消息类型必须同时更新协议头文件与接收端，并配一个协议层测试；
- 需要表达「端到端的能力协商」时，走**命令号**（老端不认 ⇒ 直接失败并降级），**不要**复用已有命令号的字段布局。

**降级必须双向安全**：新端连到老服务端时，老端只认旧字段 ⇒ 新端必须能用旧字段把功能表达完整，或者明确地不做这件事；不允许出现「新端发了老端看不懂的东西就崩」。

### 决策 3 — 锁定降级用的落地文件名，必须含每次安装唯一的分量

版本化落地文件名的形状固定为：

```
weasel[x64].<版本>.<构建>.<序号>.dll
```

`<序号>` 从 0 起，安装时探测**最小的空闲序号**：

- 探测手段复用删除动作本身。删除对不存在的文件成功、对未映射但存在的文件真删掉、对被映射的文件失败。
- 因此探测同时兼作**回收**：上一次安装留下的、已不被占用的副本会被清掉。
- 序号有上界（当前定为 64）。触到上界时名字必然仍被占用 ⇒ 写入失败 ⇒ **落回既有的降级路径**（待替换标记），行为与本决策实施前完全一致，不引入新的失败模式。

**为什么要这一条**：文件名可预测 ⇒ 同版本重装必然撞名 ⇒ 撞名必然退回待替换 ⇒ 用户被迫重启。撞名的根源不是「写不进去」，而是「名字不唯一」。

**为什么不引入常驻转发层**（「永不改名的固定入口 + 转发到真实实现」）：

- 它解决的问题与序号方案高度重叠 —— 序号方案已经让「每次安装产生新名字」这件事成立；
- 但它要多出一个二进制：需要签名、需要与系统保护进程及加载器的交互单独验证、需要自己维护转发协议；
- 收益重叠、风险显著更高。

**定位：未验证备选。** 如果未来出现「序号方案也无法覆盖的场景」（例如必须让某个外部进程始终持有一个固定路径），再以独立决策重新评估。

### 决策 4 — 门禁自身腐化必须当成回归处理

「门禁跑过了」这句话只有在门禁真的验到了目标时才成立。因此：

- **选包规则与版本命名约定脱节**属于回归，不得用「改门禁去迁就」或「改产物去迁就」草率处理。改哪一边要写进决策：本次是**门禁放宽**（版本号第四段变可选 + 兜底），因为三段式命名是刻意的设计，第四段只进内部资源与版本化文件名。
- **断言编号必须先枚举既有占用再新增**。编号重复会让机器可读报告静默损坏（重复键被覆盖），而报告正是提交的证据。
- **门禁的每个新断言都必须有一条会真失败的判别性断言**。「找到了预期的东西」通常不具判别性（旧实现会跳过而不是失败）；「没有出现不该出现的标记」才具判别性（旧实现下必然失败）。

## 后果

### 正面

- 同版本覆盖安装不再要求重启系统（在模块文件被占用的场景下也成立）。
- TSF 壳的厚度变成一个可检查的门槛，而不是靠自觉。
- 通信协议的演进有了明确边界，前后端版本错配时的行为可预测。
- 门禁的「跑过了」重新变得有意义。

### 负面 / 代价

- 落地文件名多了一段序号，排障时文件名不再直观（需要看序号判断是第几次安装的副本）。
- 用户机器上可能短暂存在多个版本的模块副本（卸载时通配清理）。
- 薄壳原则意味着「前台想知道什么」必须先设计通信协议，短期内会拖慢某些前台特性 —— 这是有意的成本。
- 门禁每次改动都需要额外自测（编码、语法、选包规则），流程变重。

### 后续行动

- 事故记录补两条：锁定降级文件名撞车（L164）、门禁自身腐化（L165）。
- 门禁新增「锁定状态下再装一遍」的阶段，把决策 3 的判别性断言固化下来。
- 决策 1 的白名单要在后续涉及 TSF 壳的评审里逐条对照。

## 备选方案与为什么不选

| 备选 | 为什么不选 |
| --- | --- |
| 常驻转发层（永不改名的固定入口） | 与序号方案收益重叠、风险更高；记为未验证备选（见决策 3） |
| 冻结版本化文件名不变 | 撞名问题原样存在；第二次同版本安装仍然退回待替换 |
| 用「时间戳」代替序号做唯一分量 | 名字长度不可控、不可预测、不便于按序号回收；序号可枚举可探测，上界明确 |
| 把条件性拦截（删词）改成无条件 | 会让「候选窗没开时按删词键」变成真删词，语义错误；冲突的正确解法是让无条件兜底让开 |
| 给被误触的开关加「每次部署复位」 | 只掩盖后果不消除冲突；且项目自禁给需要记忆的开关加复位 |
| 把门禁的选包正则改回四段式 | 等于让产物迁就门禁，与 ADR 0012 的刻意设计冲突 |
