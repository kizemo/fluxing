## §1 判据④ → 采纳替代口径「桶侧不得旧于本地」+ 6 条违例机械归因

### 1.1 裁定

**采纳替代口径，作为判据④ 的唯一口径**。ADR 0081 由 `Draft` 升 `Proposed`（升格动作由人工批准落盘，本裁定只授权口径生效）。

### 1.2 判据 v2（逐字，可直接替换 `plan-relay.md:59` 的 ④）

> ④ **桶侧不得旧于本地**：以本地侧车 `row` 全量键集为基准，逐 key 比较 `(ms, counter)` 偏序，输出四分类 `equal` / `bucket_newer` / `bucket_older` / `unmapped`。**判绿** = `unmapped = 0` **且** `bucket_older = 0`（按 1.3 归因后）。`bucket_newer > 0` 允许（HLC 单调语义下的正常前移），但 `bucket_newer > 1000` 须在 handoff 登记为观察项。**鉴别力**：同轮必须跑三份样本 —— 基线 / `badnewer` / `badolder`；`badolder` 的 `bucket_older` 必须相对基线精确 +N（本环实测 +500 ⇒ 506），`badnewer` 只增 `bucket_newer` 不得改动 `bucket_older`（实测保持 6），三份键集规模必须恒等（实测恒 94,589）。任一条不成立 ⇒ 判据本身作废，退回结果不可用。

### 1.3 6 条 `bucket_older` 的处置（四准入条款，缺一不判绿）

1. `unmapped = 0`（本环实测 **0**）—— 这是替代口径对"真实漏数据"的唯一硬拦，等价于原 `missing_in_bucket`。
2. **逐条落盘归因**：每条必须输出 `item_key / local_hlc / bucket_hlc / 归因`，落 `reports/fluxing-br-1g/judge4-v2-older-attrib.tsv`。执行方式 = 复用已取的 `tmp\relay03\r2objs\`（1,024 个 blob 已在盘）+ 扩展 `tmp\relay03\classify-r2.ps1` 输出 `bucket_older` 明细，**不重新拉 R2**。
3. **归因判据（机械、事先定死）**：`bucket_hlc.ms <= 1795565189774` ⇒ 归因为"2026-11-26 桶化首导旧批次残留，本地已前进，属 HLC 单调语义下的正常落后，不构成漏数据"。**存在任一 `bucket_hlc.ms > 1795565189774` 的 `bucket_older` ⇒ 不可归因 ⇒ 判据④ 判红**（不得改口径掩盖）。
4. 三样本鉴别力复现（见 1.2）。

### 1.4 `extra_in_bucket` 明文退出判据④（不许静默丢弃）

原口径的 `extra_in_bucket`（桶侧有、legacy 无，本环 **54,478**）**不再作为判据④ 的判红项**。理由：切读后桶侧是唯一权威源，legacy 侧"多出来的键"在切读后自然消失。**兜底**：该风险由"桶阶段 3/4 仍禁 + 规则 1 盲区未修前不得切读"约束，不由判据④ 承担。

- 桶侧 HLC 与本地侧车**逐字相同**（桶侧 `ms` 恒 `1795565189774`、counter 逐条 +1）⇒ 桶推既未篡改也未重分配 HLC；是 2026-11-26 桶化首导整库重分配了本地侧车 HLC，而老端点 D1 永久持 11-24 旧批次（`plan-relay.md:120` 已坐实）⇒ 两路**不可自愈**，逐字相等是**不可达目标**，不是待修缺陷。

## §2 判据③ → 改写为「桶推执行证明」

### 2.1 裁定

**改写**。v1 原文「③ 侧车 `brow` = 已推成功桶数」语义不可执行。

### 2.2 判据 v2（逐字）

> ③ **桶推执行证明**：同一轮日志必须同时出现 ① 至少一行 `bucket quota ` 前缀诊断行（`FormatBucketQuotaLine`，字段 `held_unproven / held_quota / rows_pushed / rows_held / quota_rows`）② 同一轮 `bucket phase=` 行的 `pushed + skipped >= 1`。**判绿** = 两条同时成立 **且** `rows_pushed <= quota_rows`。**判红** = 出现 `bucket phase=` 行但同轮无 `bucket quota` 行（桶推函数未进入配额分支），或 `pushed + skipped = 0`（闸门全关，桶推路径未被验证）。**未判定** = 日志无 `bucket phase=` 行（轮未执行）。

### 2.3 为什么不取有利读法

`brow` 是**桶级账**（每桶一行：push 成功写指纹 / skipped 写空指纹 / 未写桶保留旧行），盘上 1,024 行 = 全库桶数，不是本轮推送计数。按"历史累计 1,024 / 1,024"判绿无法区分"本轮推了 24 桶"与"本轮一桶没推"⇒ 无鉴别力，明确排除。

### 2.4 放弃的公式

原裁定单草稿的"`pushed + skipped + held = 计划桶数`"**废弃**：`FormatBucketQuotaLine` 不打"计划桶数"，`skipped` 又混多种成因，该等式不可从已印字段复原。

### 2.5 后果

本环 = **未判定**（`bucket quota` 全文件 0 命中）⇒ 阶段 2 不得判绿。取得判据③ 的唯一路径 = 一轮不早退的 `kBoth`。

### 2.6 登记项

`brow` 语义澄清写入 `stage-2-inventory.md` §3 + ADR 0077 客户端段注记，防下一环再误读。

## §3 判据② → 以「最近一个自然收尾且无 4xx/5xx 的完整轮」为准

### 3.1 裁定

**补口径，不放松**。v1 原文「② 桶拉桶数 = 服务端 `sync_buckets` 该用户行数」未定义以哪一轮为准（缺陷 ②-1）。

### 3.2 判据 v2（逐字）

> ② **桶拉完整性**：取取证批次内**最近一个**同时满足「`bucket pull` 全部分页 http 均为 2xx」与「最后一页 `has_more=0`」的轮次。该轮 `pulled_buckets` 必须等于**同期**生产只读回读的 `sync_buckets` 该用户行数，`pulled_items` 必须等于 `Σ item_count`；同期 = 同一取证批次 + 生产侧轮前轮后零写入自证。**判绿** = 逐字相等。**判红** = 该轮 `has_more=1` 或存在任一非 2xx 分页。**防作弊**：批次内**所有**轮次的分页状态必须全部落盘，不得只保留有利轮次。

### 3.3 陷阱明文

503 那页返回的 `has_more=0` 是**错误响应体解析结果**，不是自然收尾 ⇒「无 4xx/5xx」是**前置条件**，不是并列条件。缺了它，"最后一页 `has_more=0`"这条会被服务端错误吞掉。

### 3.4 依据

- 启动轮 11 页全 `http=200`、页 11 `buckets=24 items=2235 has_more=0`、收官 `pulled_buckets=1024 pulled_items=94589`，与生产 `sync_buckets 1,024 行 / Σ 94,589` 逐字相等 ⇒ 满足。
- `kBoth` 轮 `page=9 http=503` → `early_exit=bucket_pull_failed`、`pulled_buckets=800 pulled_items=73922` ⇒ 不满足。

### 3.5 后果

本环判据② = **PASS**（原文 `PASS_WITH_CAVEAT` 升为无条件 PASS，因为"以哪一轮为准"已裁定）。不影响③、④ 的独立判定。

### 3.6 登记项

`stage-2-inventory.md` §3 把 `PASS_WITH_CAVEAT` 改为 `PASS`，附 3.2 口径与 3.3 陷阱。

## §4 判据① → 改写（4xx/5xx 分流）+ 登记客户端缺陷 ①-1

### 4.1 裁定

**改写**，并且**同时**登记一个客户端缺陷。v1 原文「① 桶端点请求零 4xx/5xx」在本链写集内**不可闭合**。

### 4.2 判据 v2（逐字）

> ① **桶端点请求无客户端缺陷**：`bucket pull` 全部分页 **4xx 必须为 0**（4xx = 客户端请求构造 / 鉴权缺陷，出现任一 ⇒ 判红且当轮作废）；**5xx 逐条登记**（时间 / page / offset / 状态码 / 当轮是否早退），不单独判红。**判绿** = `4xx = 0` **且** 不存在"同一 page（同一 offset）连续两轮 5xx"（后者视为服务端持续性缺陷 ⇒ 判红）。**部分绿** = `4xx = 0` 且存在单轮单页 5xx ⇒ 判据① 记 PASS，但必须把 5xx 登记进 handoff **并**触发一次服务端可用性只读排查。

### 4.3 为什么不能保持原文

- 本链写集排除 `cloud/fluxing-sync/**`（`plan-relay.md:51`）⇒ 503 属服务端可用性，客户端**无改动空间**。
- `bucket pull` 遇非 2xx **无重试直接早退**（`early_exit=bucket_pull_failed`）⇒ 逐字口径下阶段 2 只能靠"再跑一轮碰巧无 5xx"过闸。这不是判据，是抽签。
- 但 5xx 不能全放过：正是"一次 503 就丢掉整轮 `kBoth`"让桶推路径连续四轮拿不到执行机会。

### 4.4 新登记缺陷 ①-1（客户端，属写集内，下一环修）

`bucket pull` 无有限重试 ⇒ 单次 5xx 即整轮早退。**要求实现**：同 page 5xx 重试 ≤ 2 次、退避 1s / 3s；仍失败则早退并打印 `bucket pull ... retry=<n>` 诊断行；4xx 不重试（直接早退，保持现有行为）。**验收** = 门禁用例：注入 1 次 5xx 必须重试成功且不早退；注入 4xx 必须不重试。**归属** = 接力阶段 2 前半段（与四判据重判同批，省一轮 62 分钟等待）。

### 4.5 503 根因排查（一次合并只读，不排新取证轮）

范围与边界：

- `wrangler tail`（只读）窗口 = 503 时刻（`13:05:32`）前后 5 分钟，看该请求路径与 Worker 异常；
- Cloudflare Analytics（只读）：`Workers > Errors`、`D1 > Rows read/written`、`Duration p99`；
- **只查 page 9（`OFFSET 800`）这一次**，不做泛化排查；
- **禁止**调 `/v1/auth/refresh`、**禁止**写任何生产资源；
- 同期 `rows_written_24h ≈ 13,968` 远低于盘上护栏 80,000 与免费额度 100,000 ⇒ 写预算耗尽**不是**主要假设；`auth.ts:1043-1045` 读路径刷新 `devices.last_seen`（读也写）与深偏移查询超时为两个待验假设。**结论未出之前一律记"未定"，不得写成归因**。

**不单独排取证轮**。理由：① 判据② 已由启动轮闭合；② 判据③ 需要的是"一轮不早退的 `kBoth`"，靠碰运气不可持续 ⇒ 正确顺序是**先修 ①-1 再排一轮**；③ 不加修复单纯重跑，本环已实证会被下一次 5xx 打断。

### 4.6 后果

本环判据① = **PASS**（`4xx = 0`；503 一条已登记于 `reports\fluxing-br-1g\stage2c-kboth-evidence.txt`；本环仅一轮 `kBoth`，"连续两轮 5xx"以单轮登记为限，无可判红证据）。

## §5 `WRITE_BUDGET_ROWS_PER_DAY` → 落 20,000，但执行需单独授权

### 5.1 裁定

**按 §O 拍板值 20,000 落盘**，不再重议。80,000 → 20,000 属收紧（安全方向），但不因此免授权。

### 5.2 必须同时订正的两个数字

- **单轮满推实测 ≈ 6,096 行**（§P-O 差分：`rows_written_24h` 7,089 → 13,185，已归因 2,032 / 未归因 ≈4,064）⇒ 20,000/日 ≈ **3 轮满推**，**不是** 10 轮。`plan-relay.md:66` 与裁定单里"≈2,000 行/轮"的估算必须同步订正为 6,096。
- 口径维持**每账号**（§O 已拍板，BR-②′ 全局熔断仅立项未实施）⇒ 已知边界 = 多账号时总写入 = 20,000 × N，护栏不覆盖跨账号总和。

### 5.3 执行授权（红线交互，必须写明）

`WRITE_BUDGET_ROWS_PER_DAY` 现驻 **Cloudflare Worker 生产环境变量**（D8 双口径绑定回读值 80,000），而 `plan-relay.md:143` 规定"生产 D1/R2/Cloudflare 只读"⇒ **阶段 3 是一次生产写（改 env + deploy 会替换生产 Version），必须按 `:141` 单独申请人工授权**。链内环不得自行执行。

### 5.4 阶段 3 判据补强

1. 回读必须是**服务端生效值**（`wrangler` 绑定回读），不是客户端 `wrangler.toml`；
2. 落盘后必须做一次**阈值超限负样本自证**（超限时 `code: 7500` 可复现），否则无法证明 20,000 真的生效；
3. 部署后生产 Version 必须留证（新 Version id），且 `changes:0` 的部署窗口不得计入生效证据。

## §6 接力阶段 6 **不属**桶阶段 3/4 切读禁令

### 6.1 裁定

**不属**。红线 `plan-relay.md:142`「阶段 3/4 永不启用」的主语是桶阶段状态机相位（`FLUXING_CLOUD_SYNC_BUCKET_PHASE` = 3/4），**不是**接力阶段 3/4，也不是接力阶段 6 的内部段名。

### 6.2 三条理由

1. **主语不同**：禁令对象是运行时开关相位（可一键回滚的一次性变量），阶段 6 改的是 `kDefaultBaseUrl` 主机名（`CloudAccountDialog.cpp:60-61`），属端点形态迁移。
2. **可逆性不同**：桶阶段 4 = 退役老端点代码路径，不可逆；阶段 6 自带回滚闸门（`plan-relay.md:83`「改回 `api.aiec.fun` 一个字符串」），且明令不得同批删旧端点代码。
3. **禁令目的已被单独兜住**：禁令防的是"规则 1 盲区未修 + 判据④ 未重判时切读导致半库存桶被回推（`DELETE+INSERT` 静默删条目）"；阶段 6 的硬前置第一条（`:84`「阶段 2 完成且盲区闭合」）已单独覆盖该风险。

### 6.3 但本裁定被误读的风险必须当场封死（三条约束）

1. **阶段 6 执行期间桶阶段相位必须冻结在 0 或 1**（建议 0），**不得**为 2/3/4；该项写入 `plan-relay.md:84` 硬前置，成为**第四条**。
2. 阶段 6 产出文档必须显式写明"本段切的是 HTTP 端点主机，**不是**桶阶段相位"——否则下一环会拿这条裁定去解锁桶阶段 3，而解锁它的硬前置（云端历史 40,061 条完成桶化覆盖 + 规则 1 盲区修复）**一条都没满足**。
3. `plan-relay.md:142` 红线文本**必须就地订正**为：「**桶阶段** 3/4（`FLUXING_CLOUD_SYNC_BUCKET_PHASE` = 3 切读 / 4 退役）永不启用」。这是**必做**的文档订正，不是可选；不订正则该歧义会持续产生误读。
