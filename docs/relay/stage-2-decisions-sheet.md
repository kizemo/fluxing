## 1. 判据④ 口径（结构性红 · 最硬的一项）

**原文**（`plan-relay.md:59`）：④ 按新口径重判（**判别力**：坏样本必须判红）。

**现状事实**

| 项 | 值 | 来源 |
|---|---|---|
| `legacy_keys` / `bucket_keys` | 40,112 / 94,589 | `stage2r2-judge4-hlc-compare-20261127.txt` |
| `hlc_mismatch` | 39,946 | 同上 |
| `missing_in_bucket` | 1 | 同上 |
| `extra_in_bucket` | 54,478 | 同上 |
| 原文口径裁定 | **FAIL** | 同上 |

红是结构性的：2026-11-26 桶化首导把本地侧车整库重分配 HLC，老端点 D1 永久持 11-24 旧批次
（`plan-relay.md:120` 已坐实）⇒ 两路逐字相等**不可能靠客户端修复达成**；A1 三条路线
（回退侧车 93,278 行 HLC / pull 用旧 HLC 覆盖本地 / 一次性迁移桶表）全部越红线。

**替代口径草案**（`docs\adr\0081-...-draft.md`，Status=Draft）：**桶侧不得旧于本地侧车**。

| 样本 | `bucket_vs_sidecar_equal` | `bucket_newer` | `bucket_older` | `unmapped` |
|---|---|---|---|---|
| 基线（真实侧车） | 94,583 | 0 | **6** | 0 |
| 坏样本 `badnewer`（+500 桶侧更新） | 94,083 | **500** | 6 | 0 |
| 坏样本 `badolder`（+500 桶侧更旧） | 94,083 | 0 | **506** | 0 |

判向精确偏移 500 ⇒ **口径有鉴别力**（坏样本判红成立）。

**选项**

- **A（推荐）采纳替代口径 + 6 条逐条归因**：判据④ v2 = 「无归因的 `bucket_older` 必须为 0」。
  执行前置：一次性只读取 6 条 key 的本地侧车 HLC，全部 `ms > 1795565189774`（桶化首导时刻）
  即证明这 6 条 = 11-26 之后的本地新改动、尚未上桶（因桶推路径至今未跑通）⇒ 可归因。
  归因失败的部分按**真红**处置，不放行。
- **B 采纳替代口径 + 设固定容差 6**：不查归因。**不推荐** —— 容差吃掉小规模真漏数据。
- **C 采纳替代口径，但判据④ 挂起**：先跑通桶推一轮，再判（`bucket_older` 推后必须归零）。
  逻辑最干净，但桶推已连续 4 次未执行，有死锁风险。
- **D 不采纳**：判据④ 永远红 ⇒ 阶段 2 永远不过 ⇒ 本批永久停在「双写」段。

**裁定后动作**：A/C ⇒ ADR 0081 定稿（Draft → Accepted），并把「6 条归因」结果写进 ADR §4.3；
D ⇒ 阶段 2 记为「工程不可闭合」，本批收口为双写态并另立批次。

## 2. 判据③ 口径（缺陷 ③-1：`brow` 不是推送计数）

**原文**：③ 侧车 `brow` = 已推成功桶数。

**现状事实**（`CloudSyncService.cpp:2321-2335` / `:2207-2260`，`CloudSyncService.h:575`）

- `brow` 行 = **桶级账**：push 成功写指纹 / 被 skipped 写空指纹 / 本轮未写的桶**保留旧行**
- 本轮 `pushed=0`（kBoth 早退，桶推未执行）⇒ 按「本轮」读法 1,024 ≠ 0，不成立
- 按「历史累计」读法 1,024/1,024 成立 —— 但那是把「账本行数」当「推送成功数」，无鉴别力

**关键补充**：每轮收官行 `bucket phase=1 pushed=0 skipped=0 pulled_buckets=800 …` 里
**已经**有本轮 `pushed` 字段；缺的不是计数，而是「桶推到底跑没跑」的证明。
`bucket quota` 行（`FormatBucketQuotaLine`）只在桶推函数被调用时打印 ⇒ 它是天然的
"push executed" 证据，四轮取证里**从未出现**。

**选项**

- **A（推荐）改写为执行证明**：判据③ v2 = 「本轮出现 `bucket quota` 行，且
  `pushed + skipped + held = 计划桶数`」。**零代码改动**（诊断行已存在），鉴别力强
  （未执行 ⇒ 无 quota 行 ⇒ 必红）。
- **B 改写为本轮计数**：判据③ v2 = 「本轮收官行 `pushed` = 本轮成功桶数」。
  零改动，但与现状字面重合、近乎同义反复，鉴别力弱。
- **C 保留原文 + 明确为历史累计**：1,024/1,024 判绿。**不推荐** —— 等于给一条测不出东西的判据发绿牌。
- **D 保留原文 + 记 UNDETERMINED 不动**：本环现状，会把缺陷带进下一轮。

## 3. 判据② 口径（缺陷 ②-1：原文未定"以哪一轮为准"）

**原文**：② 桶拉桶数 = 服务端 `sync_buckets` 该用户行数。

| 轮 | 结果 | 与生产 1,024 行 / 94,589 条 |
|---|---|---|
| 启动轮（`kPullOnly`，11 页） | 1,024 桶 / 94,589 条，`has_more=0` | **逐字相等** |
| kBoth 轮（page9 `503` 早退） | 800 桶 / 73,922 条 | 不等 |

**选项**

- **A（推荐）以完成的整轮为准**：被传输错误截断的轮不计入判据② ⇒ 本环 ② = PASS。
  理由：截断是判据① 的观测对象（同一缺陷不重复计红），且判据② 问的是「客户端能否把服务端
  桶账完整枚举」——启动轮已给出肯定答案。
- **B 必须无截断才能计**：本环 ② = FAIL，须复跑。
- **C 以最后一轮为准**：本环 ② = FAIL（800）。

**附条件（无论选哪项都要登记）**：② 的绿附「该轮无截断」前提；复跑须再证 1,024/94,589。

## 4. 判据① 口径 + 503（**本轮新增 · 第七项，原文六项未列**）

**原文**：① 桶端点请求零 4xx/5xx。

**现状事实**

| 轮 | 桶端点状态码 |
|---|---|
| 启动轮（11 页） | 全 200 |
| kBoth 轮 | page1–8 全 200，**page9 `13:05:32.546 http=503`** ⇒ `early_exit=bucket_pull_failed` |

**为什么必须单独裁定**：按原文逐字，阶段 2 要过，只能靠"再跑一轮碰巧无 5xx"——
这不是判据，是抽签。而且 503 **无法靠客户端写集闭合**：本链写集明确排除
`cloud/fluxing-sync/**`（`plan-relay.md:51`）⇒ 服务端改动不在授权内。

**一条待验假设（不是结论）**：503 只出现在 page9（`OFFSET 800`），前 8 页全 200
⇒ 更像**深偏移查询超时 / Worker 时长上限**，而非写预算耗尽
（同一时刻 D1 `rows_written_24h` ≈ 13,968，远低于盘上护栏 80,000 与免费额度 100,000）。
另一条可能：`auth.ts:1043-1045` 在读路径刷新 `devices.last_seen`（读也写）。
两者**均未取证**，需服务端日志或 Cloudflare 指标。

**选项**

- **A（推荐）口径拆分 + 一次合并取证**：判据① v2 = 「客户端侧 4xx 必须为 0；5xx 逐条登记，
  同一 page 连续两轮 5xx 才判红」。再排一轮取证时**同期只读**开 `wrangler tail` +
  Cloudflare Analytics 采样（不复跑单独的排查轮）。零生产写、零服务端改动。
- **B 保持原文逐字 + 复跑碰运气**：需整轮全 200 才能绿；503 再复现即再红。
- **C 保持原文 + 不复跑**：503 登记为独立服务端缺陷（新批次），本批判定维持 ① FAIL ⇒
  阶段 2 不通过，本批停在双写段。
- **D 先只读排查 503 根因，判据与取证都留到下一轮**：最保守，但要多消耗一轮人类决策。

**无论选哪项都要登记**：503 是**服务端可用性事实**，不是客户端缺陷；`bucket pull` 目前
**无重试**（遇到非 2xx 即早退），是否加客户端重试属独立代码批次，不在本单内。

## 7. 恢复链的动作（人类闸门）

裁定完成后仍是**两步**（`plan-relay.md:112`）：

1. 归档旧台账 `docs\relay.json`（留证，移入 `docs\relay\archive\`）；
2. 重跑 `docs\relay\start-relay.ps1`（重新 bootstrap）。

**为什么不能自动续链**：`relay-ledger.ps1` 拒收 `set_status=running`
（`status_running_is_human_only`）；`start-relay.ps1` 对 `status=blocked` 的台账直接
`exit 3`（`reason=ledger_blocked`）；bootstrap 只在台账**不存在**时执行。

**待明确**：这两步由人执行，还是人类在会话内一次性授权 agent 执行（`start-relay.ps1`
会新建 `status=running` 台账 ⇒ 效果等同"人类起链"，需显式授权）。
