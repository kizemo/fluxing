## 1. 取证方法（为什么这三项指标够用）

客户端要连的是一个 HTTPS 端点。一次成功连接的**必要条件链**是：

```
DNS 解析出正确 IP  →  TCP 443 建连  →  TLS 握手成功  →  HTTP 拿到业务响应
```

T103 的原始任务描述是「候选自有域名解析与握手耗时（境内多点）」。在**单机**条件下我能实测前三环，第四环（业务响应）取决于服务端是否已部署 —— 而服务端在批次 Z 才落代码，因此本报告覆盖「DNS / TCP / TLS」三环，HTTP 环用 `cloudflare.com` / `dash.cloudflare.com` / `workers.dev` 三个对照域验证「本机 HTTP 栈本身正常」。

- **DNS**：`[System.Net.Dns]::GetHostAddresses` + `Stopwatch` 计时。
- **TCP 443**：`TcpClient.BeginConnect(host, 443, ...)` + `AsyncWaitHandle.WaitOne(6000)`，**每域连跑 3 次**取 best（避免单次抖动被当成结论）。
- **TLS**：建连成功后 `SslStream.AuthenticateAsClient(host)`，记录耗时与协商到的协议/套件。
- 失败即记录**异常原文**（`不知道这样的主机。` = `WSAHOST_NOT_FOUND`），不做二次解释。

> **口径声明**：本机只有**一个**网络出口，做不到任务原文要求的「境内多点」。因此本文所有耗时为**单点实测**，跨运营商/跨省差异见 §7「未验证项」，不在此处冒充结论。

## 3. `workers.dev` 为什么必须排除：DNS 污染指纹

单看「连不上」不足以定罪 —— 可能是本机防火墙或 CF 侧故障。追加交叉取证后定性明确。

### 3.1 三个解析器给出三个不同答案，且全部非 CF 网段

数据来源：`tmp/t103/endpoint-probe.txt` 第 2 段「交叉解析器」。

| 解析器 | `workers.dev` 解析结果 | 归属（推断） |
|---|---|---|
| `223.5.5.5`（阿里） | `185.60.218.50` | Facebook 网段 |
| `119.29.29.29`（腾讯） | `103.214.168.106` | 第三方 IDC 段 |
| `8.8.8.8`（Google） | `185.60.219.41` | Facebook 网段 |
| 系统默认解析器 | `104.244.46.85` | 非 CF 网段 |

**判定**：同一个域名，四路解析给出**四组互不相同**的地址，且**没有任何一个**落在 Cloudflare 网段 ⇒ 这是 DNS 投毒的典型指纹（不同解析路径被注入不同伪造 A 记录）。真实的 `workers.dev` 通配解析应稳定落在 CF anycast 段。

### 3.2 对照域证明 CF 真网段长什么样

数据来源：同文件第 2 段「对照域」。

| 对照域 | 解析结果 | 说明 |
|---|---|---|
| `www.baidu.com` | `180.101.49.44, ...` | 国内基线正常 |
| `workers.cloudflare.com` | `104.16.197.131, ...` | **CF 真网段 `104.16.x`** |
| `dash.cloudflare.com` | `104.17.110.184, ...` | **CF 真网段 `104.17.x`** |

`workers.dev` 一个都不落在这两个段内，而正牌 `*.cloudflare.com` 稳定落进去 ⇒ 污染针对的是**这个名字**，不是 CF。

### 3.3 HTTP 栈本身正常（排除「我这边网络全废」）

数据来源：同文件第 3 段「HTTP 栈对照」。

| 目标 | 结果 |
|---|---|
| `https://cloudflare.com` HEAD | **200**，1463ms |
| `https://dash.cloudflare.com` HEAD | **403 Forbidden**（拿到 HTTP 响应 = 网络通，403 是站点策略） |
| `https://workers.dev` HEAD | **12s 超时** |

**结论**：本机 HTTPS 客户端与出口正常；`workers.dev` 的失败是「域名不可用」，不是「网络不可用」。

## 4. 对 `plan.md` R5 的验证

`plan.md` §10 R5（`plan.md:236`）原本写的是：

> 用自有域名而非平台默认域名（`*.workers.dev` 在境内可达性不稳定）

本次实测把这句话从「风险假设」升级为「**已证实的硬约束**」：

- 不是「不稳定」，是**当前网络下完全不可用**（DNS 污染 + TCP 全超时）。
- 因此 R5 不是「建议」，是**实现约束**：任何把 `*.workers.dev` 写进默认端点的方案，在境内用户机器上等于**永久同步失败**——而且失败形态是「DNS 解析到错误 IP → 连接超时」，用户看到的是**长时间无响应**而非明确报错，这是最差的失败形态（见 §6 降级口径）。

**R5 状态变更建议**：`风险` → `已闭环（实测证实，见 docs/research/fluxing-cloud-2026-11/endpoint-reachability.md）`。

## 5. 端点形态与「自定义端点」口子

### 5.1 首版端点

```
https://api.<自有域名>/v1/...
```

- 反代 / Worker 侧承载：Cloudflare Worker（与 `plan.md` 既有选型一致，不新增供应商）。
- **必须**使用自有域名而非 `*.workers.dev`：Worker 的 workers.dev 子域只是**开发预览口**，生产走自定义域。

### 5.2 自定义端点配置口子（客户端）

| 项 | 决定 |
|---|---|
| 是否存在 | **是**（否则企业内网 / 自建部署无法接入） |
| 是否暴露 UI | **否**（默认隐藏，避免普通用户误改后同步静默失效） |
| 承载位置 | 客户端配置文件（具体字段名在 Y 批次定，**不在本报告拍板**） |
| 校验 | 必须是 `https://`，必须校验证书，非 https 一律拒绝并给中文提示 |
| 与「端点不可达」的关系 | 自定义端点失败时，**不得**静默回退到默认端点（会让用户以为同步正常但数据去了别处） |

## 6. 同步失败时用户看到什么（T103 ③ 口径来源）

任务原文要求「记录『同步失败时用户看到什么』的降级口径来源（写进 T501 的错误文案）」。本机没有可运行的产品级同步链路（批次 Y/Z 尚未实现），所以**口径来源只能是被测失败形态本身**，不是用户访谈。下表把本次实测到的每种失败形态映射成文案约束：

| 失败形态 | 本次实测证据 | 客户端能否区分 | T501 文案约束 |
|---|---|---|---|
| DNS 被污染 / NXDOMAIN | `workers.dev` 四路解析全不一致；`fluxing.*` 直接 NXDOMAIN | 能（解析失败） | 「无法解析同步服务器地址」+ 提示检查网络，**不得**说「账号或密码错误」 |
| TCP 443 超时 | `workers.dev` 三次 `-1` | 能（连接超时） | 「连接同步服务器超时，请稍后重试」+ 显示已重试次数 |
| TLS 握手失败 | （未构造，属推断） | 能（握手异常） | 「与同步服务器的安全连接失败」；**不得**建议用户关闭证书校验 |
| HTTP 4xx（鉴权） | `dash.cloudflare.com` 403 证明 4xx 是「应用层拒绝」 | 能（状态码） | 按状态码分支：401/403 → 「登录已失效，请重新登录」 |
| HTTP 5xx / Worker 异常 | 未构造 | 能（状态码） | 「同步服务器暂时不可用」+ 保留本地数据，**不重试无限循环** |
| 额度 / 配额超限 | T101 侧错误码（`E_RATE_LIMIT_EXCEEDED` 等，见 `email-verify-channel.md`） | 能（业务错误码） | 明确「今日发送次数已达上限」，给「明天再试」而非「再点一次」 |

**共同约束（写给 T501）**：
1. 所有失败**必须保留本地数据**，不得因同步失败删除或回滚本地词库 —— 这是 `UserDbMerger` 语义（见 T102 报告 §4）之外的额外产品约束。
2. 失败文案**必须可区分「网络不可达」与「凭据错误」**：本报告 §3 证明这两种在真实网络里都会发生，混为一谈会让用户改密码改成死循环。
3. **不得**出现「已同步」但实际未上传的状态（静默失败是最坏结果）。

## 8. 复跑指引（本报告结论可自证）

探针是一次性 PowerShell 脚本，不落仓库（`tmp/` 已被 gitignore）。重跑要点：

```powershell
$ErrorActionPreference='Stop'
# DNS：每域 1 次，记录 Stopwatch 毫秒与全部 IP
[System.Net.Dns]::GetHostAddresses($d)
# TCP：BeginConnect + AsyncWaitHandle.WaitOne(6000)，跑 3 次取 best
# TLS：SslStream.AuthenticateAsClient($d)，记录 SslProtocol 与 NegotiatedCipherSuite
```

- **必须**用 `Start-Process -WorkingDirectory` 或 `[System.IO.File]::WriteAllText` 落盘，不要 `Set-Location` 后写文件（本机安全策略会拦）。
- 交叉解析器：`Resolve-DnsName -Name 'workers.dev' -Type A -Server 223.5.5.5 -DnsOnly -QuickTimeout`（另换 `119.29.29.29` / `8.8.8.8`）。
- 中文异常文本落盘用 UTF-8 无 BOM，否则控制台 cp936 会乱码。
- **判据复现**：若 `workers.dev` 在某网络下三连 TCP 成功、且解析落在 `104.16.x` / `104.17.x`，说明该网络未被污染 —— 这**不推翻**本报告结论，只说明污染是**按网络/按地区**发生的，因此「默认端点不依赖 `workers.dev`」依然是唯一安全解。
