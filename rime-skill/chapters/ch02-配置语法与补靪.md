# Chapter 2: 配置语法与补靪

## Core Idea

Rime 配置是**带编译指令的 YAML**：`__include` / `__patch` / `__append` / `__merge` 是编译器指令，用户的 `patch:` 是它们的语法糖。路径是一套 DSL（`/` 分层、`@n` 选列表项、`/+` 合并、`/=` 替换），不是字符串替换。

## Key Concepts

| 指令 | 层 | 作用 |
|---|---|---|
| `patch:` | 用户层 | 用户在 `<配置>.custom.yaml` 里写的补靪 |
| `__patch:` | 编译器层 | 源文件内部，修改相对路径下的子节点 |
| `__include:` | 编译器层 | 在当前位置包含另一 YAML 节点（可跨文件） |
| `__append:` / `__merge:` | 编译器层 | 往列表追加 / 往 map 合并 |

**编译器插件自动做的事**：源文件根节点若没写 `__patch:`，会自动插入 `__patch: <config>.custom:/patch?`——这就是用户写 `patch:` 就能生效的原因。**但根节点一旦自己用了 `__patch:`，自动补靪就不再插入**，此时必须显式把 `<config>.custom:/patch?` 列进 `__patch:` 列表。

**执行顺序（同一节点下）**：`__include:` → 合并本节点其他 key-value → `__patch:` 修改子节点。注意 YAML map 无序，书写顺序不决定先后。

## Reference Tables

### 路径 DSL

| 写法 | 含义 |
|---|---|
| `key/alpha` | 逐层下钻。**key 本身不能含 `/`** |
| `some_list/@0/x` | 第 0 个列表项（从 0 起） |
| `some_list/@last/x` | 末项（不论长度） |
| `'some_list/@before 0/x'` | 在第 0 项之前插入 |
| `'some_list/@after last/x'` | 在末项之后插入 |
| `some_list/@next/x` | 末尾追加（`@after last` 简写） |
| `some_list/+` | 与列表合并 |
| `some_map/+` | 与字典合并 |
| `some_list/=` | 用给定值整体替换 |
| `default.custom:/patch?` | 引用另一文件的节点；路径以 `?` 结尾时**目标不存在不报错** |

原文明确建议：**`@before` / `@after` / `@next` 不建议在补靪中使用**。

### 指令示例

```yaml
# 包含（同文件 / 跨文件 / 整文件）
__include: local/node
__include: config:/external/node
__include: config.yaml:/

# 补靪：替换 / 合并 / 整体替换
__patch:
  sibling: new value
  append_to_list/+:
    - appended item
  replace_map/=:
    only_key: value

# 引用另一组补靪
__patch:
  - company_standard
  - team_convention
```

## Worked Example：为什么你的 patch 会「完全无效」

这是本项目实测过的 librime 行为级陷阱（`output/data/user-custom/rime_ice.custom.yaml` 注释里有完整记录）：

```yaml
# 源 schema（rime_ice.schema.yaml）里是这样引入默认标点表的：
punctuator:
  half_shape:
    __include: default:/punctuator/half_shape
```

你想覆盖 `/` 键，于是写：

```yaml
# 错误写法 —— patch 静默失效
patch:
  punctuator/half_shape:
    '/': '、'
```

**为什么失效**：librime 的 `DependencyPriority` 是 `kPatch=2 > kInclude=1`，**patch 比 include 先执行**。patch 那一刻 `half_shape` 还是那个 `__include` 字符串，不是 map，于是 dict-merge 静默失败——不报错，patch 直接被丢弃。

**正确写法**：在 patch 里**重述 include**，让 overrides 落到被包含的内容之上：

```yaml
patch:
  punctuator/half_shape:
    __include: default:/punctuator/half_shape
    '/': '、'
```

验证方式：部署后看 `build/rime_ice.schema.yaml` 的 `punctuator/half_shape` 里有没有你的覆盖。

## Anti-patterns

- **在 `.custom.yaml` 里写 `__patch:`** —— 用户层用 `patch:`；`__patch:` 是源文件里的编译器指令。
- **把 `patch:` 写两遍** —— YAML 同名键后者覆盖前者，无警告。
- **用 `/` 表达含斜杠的键名** —— 路径按层切分，无法表达。
- **含特殊字符（`/` `+` `=` `*`）的路径用双引号** —— 转义踩坑；用单引号。
- **以为 `__include` 的内容可以整段覆盖** —— 覆盖 `half_shape` 这类被 include 的节点，必须重述 include。
- **以为 `patch` 会在 `include` 之后执行** —— 恰恰相反，这是上面那个陷阱的根因。

## Key Takeaways

1. `patch:` 是用户层入口，`__patch:` 是编译器层指令，混用会静默失败。
2. 路径是 DSL：分层、列表下标、合并/替换算符各有语法。
3. patch 先于 include 执行 —— 覆盖被 include 的节点时必须重述 `__include:`。
4. 编译器只处理源文件；`installation.yaml`、`user.yaml` 不走编译。
5. 编译结果合并为 `default` + 各方案配置，不是一一对应。
