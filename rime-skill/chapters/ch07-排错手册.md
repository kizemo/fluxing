# Chapter 7: 排错手册

## Core Idea

Rime 的故障绝大多数不是「引擎坏了」，而是**三件事之一**：没部署、patch 写法不对、补丁打在了 `__include` 引入的节点上。本章给一个**固定的排查顺序**，先查最可能的。

## 排查顺序（照着走，别跳）

```
1. 部署了吗？          → 没部署 = 没改。重新部署再谈别的
2. build/ 里有吗？     → 看 <用户文件夹>/build/<name>.schema.yaml 有没有你的值
                        没有 → patch 没进编译（查 3、4、5）
                        有但行为不对 → 配置生效了，是语义问题（查 6、7）
3. patch: 只有一份吗？ → 同一文件出现两个 patch: 键，后者覆盖前者
4. 节点是 __include 引入的吗？→ 是 → 必须在 patch 里重述 __include:（见 ch02）
5. 路径语法对吗？      → / 分层、@n 选列表项、/+ 合并、/= 替换；key 不能含 /
6. when 条件对吗？     → paging 要先翻过页；always 排最后
7. 修饰符与键名对吗？  → 顺序 Shift→Control→Alt；键名大小写敏感
```

## Reference Tables：症状 → 原因 → 处理

| 症状 | 原因 | 处理 |
|---|---|---|
| 改了配置完全没反应 | 没重新部署 | 重新部署；再看 `build/` |
| patch 无声失效 | 目标节点是 `__include` 引入的 | 在 patch 里重述 `__include: default:/<节点>` 再写覆盖 |
| 部署报 `invalid key binding #N, with invalid accept pattern` | 键名拼错/大小写错 | 查 X11 keysym（去 `XK_` 前缀）；日志里的 #N 直接定位到第 N 条 |
| 整个 `bindings` 段失效 | 写成了 list 而不是 list of map | 写成 `- {when:…, accept:…}` |
| `when: paging` 没生效 | `paging` 要先有 `Page_Down` 触发过 | 改 `has_menu` |
| `Shift+Tab` 没反应 | 修饰符顺序错 | 固定 `Shift+Tab`，不是 `Tab+Shift` |
| 单独 Shift 切不了中英（小狼毫） | **前端把 Shift 整段吃掉**，librime 根本看不到这个键 | yaml 层做不到（`ascii_composer/switch_key` 也一样收不到）；小狼毫/火流猩只能走服务端状态机 |
| 中文标点怎么输都不对 | `recognizer/patterns/punct` 覆盖了 punctuator | 把 `key_binder` 放到 `engine/processors` 头部 |
| `Control+grave` 没反应 | 大小写或修饰符拼错 | 字面字符**加引号** |
| `Ctrl+Shift+9` 切不动标点 | **前端发的是 `(` 不是 `9`**（小狼毫/火流猩发字符不发键码），不是被系统级 hotkey 抢 | 改用 `Control+Shift+numbersign` |
| 换方案后繁简/中英状态变了 | 开关跨方案继承 | 显式 `reset`，或用独立开关名 + `simplifier/option_name` |
| 候选里出现 ☯ 阴阳鱼 | 混元编码器猜的词，码表里没有 | 确认是否要这个结果；或关 `translator/enable_sentence` |
| 候选重复（「钟」出现两次） | `simplifier` 没配 `uniquifier` | engine/filters 里加 `uniquifier` |
| 繁简一字对多简出错（乾） | OpenCC 对生僻词组/专名覆盖不到 | 手工订正；必要时改用固态词典 |
| 粤拼提示的多音字标错 | 程序自动注音不保证正确 | 不要当标准学 |
| 用户词典工具报错 | 输入法还在运行，独占词典 | 关掉输入法再跑 |
| 部署后方案菜单能开但方案不可用 | 方案没部署成功 | 看日志定位（`INFO` 日志里 `E` 开头的行） |
| 中文输入法在某些程序里自动开启又不想开 | 没配 `app_options` | macOS 用 Bundle Identifier，Windows 用小写程序名 |

## Worked Example：一个「patch 写了但完全无效」的完整排查

**现象**：写好了

```yaml
patch:
  punctuator/half_shape:
    '/': '、'
```

**期望**：按 `/` 输出「、」。**实际**：仍输出 `/`，部署日志一条错误都没有。

**按顺序走**：

1. 部署了吗？→ 部署了，`build/` 里也有 `punctuator/half_shape` 段。
2. `build/` 里有我的值吗？→ **没有**。→ 说明 patch 根本没进编译结果。
3. `patch:` 只有一份吗？→ 只有一份。
4. 目标节点是 `__include` 引入的吗？→ 查源 schema：`punctuator/half_shape: {__include: default:/punctuator/half_shape}` —— **是**。
5. 结论：kPatch(2) > kInclude(1)，patch 先于 include 执行，此时节点还是 `__include` 字符串，dict-merge 静默失败。

**修复**：

```yaml
patch:
  punctuator/half_shape:
    __include: default:/punctuator/half_shape
    '/': '、'
```

**验证**：重新部署 → `build/<name>.schema.yaml` 的 `punctuator/half_shape` 里有 `'/' : '、'` → 现场按 `/` 输出「、」。

**教训**：dict-merge 失败**不报错**。所以「没报错」不等于「生效了」——**以 `build/` 为准**。

## 调试技巧

1. **删了重建**：把 `<name>.custom.yaml` 改名移走，部署一次看 baseline 行为。
2. **二分 patch**：patch 太大就拆两半，看哪一半出锅。
3. **看 build/**：部署后的合并结果，直接看 binding 是否如预期。
4. **看 INFO 日志**：出现 `invalid key binding` 能直接定位到 `key_binder/bindings` 第 N 条。

## Anti-patterns

- **不部署就断言"配置无效"** —— 编译结果根本没更新。
- **只看源文件不看 `build/`** —— 源文件对，合并结果可能不对。
- **把「无报错」当作「已生效」** —— dict-merge 失败是静默的。
- **一次改一大片** —— 出问题时无法二分定位。
- **把 warning 当噪音** —— `invalid key binding` 直接对应第 N 条绑定。

## Key Takeaways

1. 排查顺序固定：部署 → build/ → patch 键 → include 冲突 → 路径 → when → 键名。
2. 静默失效的最大来源是 `__include` 优先级，其次是重复 `patch:`。
3. `build/` 是唯一可信证据；日志是定位工具。
4. 修饰符顺序固定 `Shift → Control → Alt`；键名大小写敏感。
5. 改动越大越难定位——一次改一个变量。
