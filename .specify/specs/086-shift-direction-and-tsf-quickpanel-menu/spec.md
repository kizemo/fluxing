# 086 - 左右 Shift 上屏候选方向修正 + 输入法弹出菜单补齐「快速面板常驻」

## 0. 背景

用户于 2026-10-28 装机实测 1.1.0 后给出 8 条反馈。其中 **4 条需要处理**，本条覆盖其中 2 条：

- **反馈 4**：托盘右键菜单里**找不到**「快速面板常驻」，只有「快捷设置栏」。而常驻开关是上一条（spec 084 / ADR 0013）刚刚交付给用户的。
- **反馈 5**：裸 Shift 能上屏第 2 / 3 候选了（上一条已修好「不能上屏」），但**左右颠倒**——按左 Shift 应上屏第 2 个候选，实际上了第 3 个；右 Shift 应上第 3 个，实际上了第 2 个。

另外 2 条（CapsLock 打开后候选窗消失、快捷键全失效）经本轮取证**定性为部署侧问题**而非代码缺陷：装机时 64 位的前端 DLL 被系统占用而未能替换，安装器已按既有机制排好开机补换，但机器尚未重启 ⇒ **本条不改这部分代码**，改在交付报告里给出换装指引。

⇒ 上一条（spec 084 / ADR 0013）交付的「快速面板常驻」**只在服务端托盘图标菜单里有**，用户是从**输入法弹出菜单**（语言栏右键）进入的，那条路径上根本没有这一项。⇒ 上一条的验收项 T013 之所以没被用户发现，不是用户漏看，而是**入口本身缺项**。

## 1. 目标

1. 左 Shift 裸按上屏第 2 个候选、右 Shift 裸按上屏第 3 个候选，左右不再颠倒。
2. 输入法弹出菜单里出现「快速面板常驻」，且点它能真正生效。
3. 两侧的「左右」约定只有**一处**定义，杜绝今后再出现单端漂移。

## 2. 用户故事

- **US086-A**：作为用户，我用左 Shift 上屏第 2 个候选、用右 Shift 上屏第 3 个候选，左右符合直觉。（验收 SC-086-1）
- **US086-B**：作为用户，我在输入法弹出菜单里能找到「快速面板常驻」，勾上后快捷设置栏不再自动隐藏。（验收 SC-086-2 / SC-086-3）
- **US086-C**：作为维护者，我希望「左 / 右」这件事在代码里只有一个定义，改动任何一端都不可能再把方向改反。（验收 SC-086-4）

## 3. 功能需求

- **FR-086-A（US086-A）**：Shift 状态上报通道里承载「本次是左 Shift 还是右 Shift」的那一位，其含义必须与既有的线缆约定一致（**0 = 左，1 = 右**）。
- **FR-086-B（US086-A）**：左 / 右的**编码**与**解码**必须由**同一对函数**产生与消费；两侧不得各写一份字面量。
- **FR-086-C（US086-B）**：输入法弹出菜单（简体中文 / 繁体中文 / 英文三个语言版本）必须包含「快速面板常驻」项，且该项的命令编号与既有服务端实现一致。
- **FR-086-D（US086-B）**：从弹出菜单点选该项后，效果与从托盘图标菜单点选**完全一致**（面板常驻 / 取消常驻）。
- **FR-086-E（US086-C）**：新增一条回归断言，钉死「左编码为 0、右编码为 1、左右各自往返后不变」。

## 4. 非目标

- **不新增进程间通信消息类型**。该项复用既有的「托盘命令」通路，服务端已有该命令的处理器，无需扩协议。
- **不给输入法弹出菜单加勾选标记**。常显开关的当前状态只显示在服务端托盘菜单里；要在弹出菜单上也显示，需要新增一条「查询开关状态」的往返消息，属于协议扩张，留作后续条目。
- 不改 Shift 状态机本身的判定逻辑（何时该上屏、上屏第几个候选），那些在上一条已验证正确。
- 不改 CapsLock 相关的任何代码（反馈 1 / 2 已定性为部署侧问题）。
- 不动输入引擎本体（上游只读引用；宪法 P3）。

## 5. 验收标准

### 5.1 行为验收

- **SC-086-1（US086-A）**：左 Shift 裸按上屏**第 2** 个候选，右 Shift 裸按上屏**第 3** 个候选。
- **SC-086-2（US086-B）**：输入法弹出菜单（三个语言版本各一）**均可见**「快速面板常驻」。
- **SC-086-3（US086-B）**：从弹出菜单勾选该项后，快捷设置栏不再自动隐藏；再点一次恢复自动隐藏；效果与托盘图标菜单路径一致。
- **SC-086-4（US086-C）**：新增回归断言全绿；且该断言**对修复前的错误实现会失败**（即它能证伪，而不是恒真）。

### 5.2 工程验收

- **SC-086-5**：改动文件通过格式检查（基线本就干净的文件保持干净）；整解构建通过；全套件通过。
- **SC-086-6**：安装包部署后复跑门禁通过（源绿 ≠ 产物绿）；且**装好的弹出菜单里确实含有该项**（对构建产物做资源级检查，而不是只看源码）。

### 5.3 取证记录（修复前）

**缺陷 A · 左右颠倒（反馈 5）**

| 环节 | 事实 |
|---|---|
| 1 · 契约 | 线缆约定写死：**第 0 位 = 0 表示左、1 表示右**；既有测试的注释与两条断言都据此写 |
| 2 · 发送端 | 客户端按约定编码（左→0、右→1），**符合契约** |
| 3 · 接收端 | 服务端把同一位**反着读**（读成「1 = 左」），与契约相反 |
| 4 · 后果 | 送进状态机的「是否左 Shift」与真实按键相反 ⇒ 左 Shift 走右 Shift 分支（选第 3 个），右 Shift 走左 Shift 分支（选第 2 个） |
| 5 · 排除项 | 键名映射（扫描码 → 左右）、状态机内的「左/右 → 第几个候选」映射、发起端对左右 Shift 的判定，**全部正确** ⇒ 错点唯一，就在接收端那一处 |

⇒ 修复方向：把「编码」与「解码」收敛到**同一对函数**，两端都调用它。单改一端（只把服务端那一行反过来）也能修好症状，但**下一次有人动这一行仍可能再漂移**；同源化之后，「改反」这件事在结构上不再可能发生。

**缺陷 B · 弹出菜单缺项（反馈 4）**

| 环节 | 事实 |
|---|---|
| 1 · 现象 | 服务端托盘图标菜单里**有**「快速面板常驻」，输入法弹出菜单里**没有** |
| 2 · 资源 | 两处菜单是**两份独立的资源**：服务端一份，输入法前端一份（三个语言版本）。上一条只改了服务端那一份 |
| 3 · 路由 | 前端弹出菜单的选中项经既有通路转发到服务端的命令处理器，服务端**已有**该项的处理器 ⇒ **路由不缺，缺的是菜单项本身** |
| 4 · 编号 | 该命令编号只定义在服务端自己的头文件里，前端使用的共享头文件里**没有** ⇒ 前端资源里根本写不出这一项 |
| 5 · 后果 | 用户从输入法弹出菜单进入，**永远看不到**这一项；只有从托盘图标菜单进入才看得到 ⇒ 上一条的验收项无法被用户自行发现 |

⇒ 修复方向：共享头文件补上该命令编号；输入法前端三个弹出菜单各补一项。**不扩协议**（既有通路已经够用）。

### 5.5 遗留（不在本条内）

- 弹出菜单**没有勾选标记**：常显开关的当前状态只在服务端托盘菜单可见。要在弹出菜单上也显示，需新增「查询开关状态」的往返消息 ⇒ 协议扩张，留后续条目。
- 反馈 1 / 2（CapsLock）：部署侧问题，需用户重启完成换装后复测，**本条不含任何相关代码改动**。
