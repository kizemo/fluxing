### 2.2 客户端侧（现行顺序 = 根因）

> ⚠️ 本节行号取自**基线提交 `d4b5108`**（HEAD）；在途实现（`tasks.md` T110）已移动这些行 —— 本节描述的是**根因基线**，不是当前工作树。

`CloudSyncCoordinator::SyncOnce`（基线 `WeaselServer/Cloud/CloudSyncService.cpp:888`）现行顺序：

```
LoadSidecar(:941) → BeginMaintenance(:945) → ExportUserDict(:967) → 条目化(:994)
  → 分配/复用 HLC(:1003-1020)  ← ★ 此刻还看不到远端
  → 拉远端(:1022-1086)
  → 合并(:1088) → 回写本地(:1092) → 推送集合(:1134) → 推送(:1157) → 侧车重建(:1240) → SaveSidecar(:1276)
```

- 「本地改动过」的判定**只**看侧车里的载荷哈希（`:1009-1019`）：哈希变了 ⇒ 分配新墙钟 HLC ⇒ 标记本地改动。
- **侧车丢失 ⇒ 全部本地条目哈希都「变了」⇒ 全部分配新墙钟 HLC ⇒ 全部进推送集合 ⇒ 服务端守卫失效（墙钟 HLC 必然大于云端旧 HLC）⇒ 40,061 行全部重写（≈ 80k 行写入）**。
- 客户端**已经在同一轮里拉取并解密远端副本**（`:1061` 解密）⇒ **远端明文就在手上**，只是「分配 HLC」发生得太早，没机会用。

⇒ **根因不是「每次都推全量」，而是「侧车丢失 ⇒ 无法证明『本地这条就是云端那条』⇒ 只能当成新数据重写」**（与批次 BR 交接 §0 的结论一致）。

## 3. 总体方案

**一句话**：把「分配 / 复用版本号」挪到「拉远端之后」，让客户端有机会**证明**本地条目就是云端那条；证明成立就**沿用远端版本号**（服务端守卫必然命中 ⇒ 零写入），证明不成立就先**压后**（宁可晚点同步，也别重写云端）。

```
一轮同步（新顺序，a-1）
  ① 读侧车（游标 / 行）
  ② 进入维护态 → 导出本地 → 条目化 → 退出维护态（只读导出，不持锁做网络）
  ③ 拉远端（分页；扫描模式下从扫描游标继续）
  ④ 对账（★ 本批核心）：
       ├ 远端命中且明文逐字节相等  → 沿用远端版本号、不标记改动、不推送   （R1 · a-2）
       ├ 远端命中但明文不同        → 视作本地改动：新墙钟版本号 + 推送     （R4 · a-5）
       ├ 远端未命中且库存未扫完    → 压后，本轮不推                        （R2 · a-3）
       └ 远端未命中且库存已扫完    → 真正新增：分配版本号 + 推送             （常规语义）
  ⑤ 合并（版本大者胜）→ 回写本地（远端带来的新词 / 更新）
  ⑥ 推送（分批；只推「本地改动过」的条目）
  ⑦ 重建侧车（沿用命中项与远端胜出项**携带远端版本号**）      （R3 · a-4）
  ⑧ 无条件诊断行（成功 / 失败都打）                            （R5 · a-6）
```

**零写入的因果链**（a-2）：

```
本地明文 == 远端明文（逐字节）
  ⇒ 该条目就是云端那条的当前版本
  ⇒ 沿用远端版本号 R
  ⇒ 若提交：服务端 stored == R ⇒ compareHlc(stored, R) >= 0 ⇒ skipped（零写入）
  ⇒ 而本方案**根本不提交**它 ⇒ 更不会写
```

## 4. 详细设计

### 4.1 R0 · 顺序倒置（a-1）

- 把 `:1003-1020` 的「分配 / 复用 HLC」整块**移到拉取之后**（`:1086` 之后、合并之前）。
- 依赖：拉取需要 `last_server_seq_`（来自侧车游标）⇒ 顺序倒置**不影响**游标来源。
- 维护态窗口：现行代码在**整轮**（含网络 I/O）都持维护态。顺序倒置不改变这一点 ⇒ 不引入新的锁行为（NFR-007 不破）。
- **注意**：改序后「本地是否改动」的判定输入从「侧车哈希」扩展为「侧车哈希 + 本轮远端明文」，判定函数必须**同时**消费两者（见 4.2）。

### 4.2 R1 · 远端版本沿用（a-2 · 零写入主体）

**判别条件（FR-003，不可替换）**：本地条目的**明文载荷**与远端条目的**明文载荷**（都已解密、都是条目载荷字段本身）**逐字节相等**。

- 两侧载荷同构：本地侧由 `DictRowsToEntries`（`:994`）产出，远端侧由 `OpenItemsTolerant`（`:1061`）产出，字段同为「键 + 载荷 + 版本号」⇒ 直接比载荷字符串即可。
- **不得**比：密文（nonce 随机 ⇒ 必不等）、版本号（版本号正是待决定的东西）、长度、哈希近似。
- 命中后的三件事（a-2 原文）：
  1. `L.hlc := R.hlc`（沿用远端版本号，**不**分配新的）；
  2. **不**标记本地改动 ⇒ 不进推送集合（`:1134-1155` 的集合构建处直接跳过）；
  3. 侧车记 `(键, R.hlc, sha256(载荷))`（见 4.4）。
- **与本地时钟的关系**：沿用远端版本号后仍要 `HlcObserve`（把远端版本喂给本机时钟）⇒ 本机后续写入的版本号不会低于远端（防止下一轮又被远端压回去）。

### 4.3 R2 · 库存未证实不推送闸门（a-3）+ 实施解释

**a-3 字面条件**：本轮拉取起始游标 `pull_start_cursor == 0`（= 从零做全量库存扫描）**且**本轮结束时 `has_more == true`（库存未扫完）⇒ 本轮不得推送「既无侧车记录、又不在本轮远端集合里」的本地条目。

**实施解释（本批登记的唯一一条偏差，见 `spec.md` §8-6）**：闸门取 a-3 的**超集**口径 ——

| 项 | a-3 字面 | 本批实施（超集） |
|---|---|---|
| 触发条件 | `pull_start_cursor == 0` **且** `has_more == true` | **仅** `has_more == true`（本轮没把云端库存扫完） |
| 解除条件 | 下一轮从零重扫时再判 | 某轮结束时 `has_more == false`（库存扫完） |
| 覆盖轮次 | 仅扫描首轮 | 扫描期**逐轮**持续生效 |

- **依据**：a-8①「扫描未完成的轮次零写入」与 AC-01 判据（写入增量 = 0）。若闸门只覆盖首轮，第 2 轮起（游标 > 0）会把「本轮尚未见到」的本地条目当成新增推送 ⇒ 写放大原样复现 ⇒ **判据不成立**。a-3 的字面条件是本口径的**特例**（首轮）。
- **副作用（如实登记）**：侧车完好（游标 > 0）时，只有「云端库存比游标多出超过单轮拉取上限（1,000 条）」才触发闸门 ⇒ 该情形下**新增本地词条被延后**到扫完那一轮（延迟，不丢数据，见 `spec.md` §8-1）。
- **实现落点**：`const bool inventory_unproven = has_more;`（`CloudSyncService.cpp` 对账段）。

**扫描状态不落盘 ⇒ 侧车格式逐字不变（a-3）**：

- 闸门是**每轮从服务端当场判定**的（`has_more`）⇒ **无需**把「扫描进行中」持久化。
- 扫描进度由侧车**既有游标**承载（游标本就记录拉取进度、逐轮推进）⇒ 侧车的行结构 / 字段 / 取值域**一律不变**，零新增状态面（FR-005）。
- 「侧车 `seq` 行负值编码」方案**已放弃**：闸门不依赖持久化状态 ⇒ 负值编码多余，且会扩展既有字段取值域（与 a-3「格式不变」冲突）。
- 侧车丢失 ⇒ 游标归零 ⇒ 从 0 起分页扫完整库存 ⇒ 与 a-3 字面情形一致。

**闸门的作用对象**：「既无侧车记录、又不在本轮远端集合里」的本地条目 ⇒ 本轮**压后**（不进推送集合，**也不**写侧车行 ⇒ 下一轮继续待证）。库存扫完后仍未证实的 ⇒ 真正新增 ⇒ 正常推送。

### 4.4 R3 · 侧车重建（a-4）

- 侧车行来源（现行 `:1240-1274`）需**增补一条分支**：**R1 命中项**（远端胜出判定为「否」，因为版本号相等且载荷相等）也必须写成「已同步」行，且携带**远端版本号** + 载荷哈希。
  - 现状：`synced` 判定为「远端胜出」或「本轮推成功 / 被跳过」两条；R1 命中项两者皆否 ⇒ 会被判为「未同步」⇒ **侧车不记它** ⇒ 下一轮又变成「无侧车记录」⇒ 退化为压后项 ⇒ **必须补这条分支**。
- 「远端胜出」条目（云端有、本机无）本来就写行且携带远端版本号 ⇒ 现状已满足 a-4。
- **逐轮重建**：扫描期每轮都用「本轮已知的远端条目 + 既有侧车行」重建侧车 ⇒ 扫描完成后侧车覆盖全部已证实的条目 ⇒ 回到常规增量。
- 压后项**不写行**（无远端版本号可写）⇒ 保持「未证实」状态 ⇒ 下一轮继续对账。
- **游标照常推进**：侧车 `seq` 行记录本轮拉取进度（既有语义，不变）⇒ 扫描进度天然跨轮存活（见 4.3「扫描状态不落盘」）。

### 4.5 R4 · 分歧条目本地胜出（a-5）

同键、明文**不同** ⇒ 分歧，**两个子情形**（与优化前逐字一致）：

| 子情形 | 判据 | 结果 |
|---|---|---|
| ① 本地没改过 | 侧车**有**该键的记录且载荷哈希**未变** | **远端胜出、不回推**（服务端已握着更新版本） |
| ② 本地改过 / 侧车丢失 | 侧车**无**该键的记录，或哈希**已变** | **本地胜出**：分配新墙钟版本号（`HlcTick`）⇒ 进推送集合 |

- 版本号方向天然保证子情形 ② 的本地胜出：**先 `HlcObserve` 吸收本轮全部远端版本**，再分配新墙钟版本号 ⇒ 本机新版本 ≥ 远端版本 ⇒ 合并保留本地（否则设备时钟超前 / 本机时钟回拨时，本地分歧条目会输给远端，R4 落空）。
- **已知代价如实登记**（`spec.md` §8-2）：侧车丢失后丧失「按版本定序」能力，可能覆盖另一台设备的更新版本 ⇒ 本批**不修**。

### 4.6 R5 · 诊断行（a-6）

- 格式固定：`[cloudsync] reconcile scan_complete=<0|1> matched=<n> deferred=<n> divergent=<n> pushed=<n>`。
- 五个计数含义：`scan_complete` = 本轮结束时库存是否扫完；`matched` = R1 命中数；`deferred` = 压后数；`divergent` = 分歧数；`pushed` = 本轮推送数。
- **无条件**：本轮失败也照打 ⇒ 实现上以「统一出口打点」实现（成功与各条失败出口都要覆盖），不依赖界面显示。
- 落点：既有诊断通道 `diag::AppendLine("cloudsync", ...)`（同 `:1204` 的用法）⇒ 不引入新的日志体系。
- **不得**含口令 / 密钥 / 令牌 / 邮箱 / 词库明文（只放计数与布尔值）。

### 4.7 计数承载与诊断格式

- 五个计数装在**新增的 `CloudReconcileStats` 结构**里（`WeaselServer/Cloud/CloudSyncService.h`）⇒ 与「本轮结果」结构解耦。
- 诊断行的**逐字格式串**放在**生产头**里（`inline std::string FormatReconcileDiagLine(const CloudReconcileStats&)`，同一头文件）⇒ 单测断言的就是生产会写出的那一行（宪法 R7：不复制第二份格式串）。
- `CloudSyncRoundResult`（`WeaselServer/Cloud/CloudSyncEngine.h:69-77`）**不改** ⇒ 引擎与界面零感知；既有界面文案不变（`AccountSyncStatusTextSuccessWithNotices` 的入参不变 ⇒ 无用户可见文案变化 ⇒ 无 CHANGELOG 条目义务，宪法 P5）。
- 计数口径：`scan_complete` = 本轮结束库存是否扫完（**只推不拉的轮次没有库存视图 ⇒ 记 0**，不谎称扫完）；`matched` = R1 命中数；`deferred` = 压后数；`divergent` = 走「本地胜出 + 进推送集合」的分歧数；`pushed` = 本轮被服务端**接受**的条目数（skipped 不计）。

## 8. 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| **服务端按明文哈希去重**（上传内容哈希，服务端比对） | 会泄漏词条指纹、破坏端到端密文语义；ADR 0076 D2-2 已明确关闭，不重复讨论 |
| **服务端加「按条目查存在」接口** | 改服务端 ⇒ 需重新部署 + 协议变更 ⇒ 越出 a-8④ 的范围；且服务端仍无法在密文域判断「内容是否相同」 |
| **客户端提交「最小版本号」（版本号取 0）试探存在性** | 服务端守卫会跳过已存在的条目（零写入）✔，但**无法区分**「云端有同一条」与「云端有旧版本」⇒ 分歧条目的本地胜出会被静默吞掉 ⇒ **丢用户改动**，否决 |
| **本机维护一份内容哈希云端索引** | 等于把内容指纹放到云端 ⇒ 破坏 E2E 语义（与 D2-2 同理） |
| **单轮一次性扫完整个库存**（把单轮页数上限拉高） | 单轮 40k 条 ≈ 401 次拉取 ⇒ 维护态被长时间占用（影响打字，宪法 P2 精神）；且突破客户端每日拉取次数口径 ⇒ 改为**多轮扫描 + 逐轮零写入** |
| **侧车 `seq` 行负值编码扫描状态** | 闸门改为每轮由服务端当场判定（`has_more`）⇒ **无需**持久化扫描状态 ⇒ 负值编码多余，且会**扩展既有字段取值域**（与 a-3「侧车文件格式不变」冲突）⇒ 否决 |
| **新增独立的「扫描状态文件」** | 功能上可行，但会在用户数据目录**新增一个文件** ⇒ 扩大「状态丢失面」与备份清单（另一议题 BR-①d）⇒ 否决 |
| **改侧车文件格式（新增一行记录扫描游标）** | a-3 明令「侧车文件格式不变」⇒ 否决 |
| **把本地同步状态文件搬进备份 / 迁移清单** | 属另一议题（BR-①d，ADR 0076 D2-6）⇒ 本批不做 |

## 10. 与其他 spec / ADR 的边界

- **spec `100-fluxing-cloud-account-sync`**：101 是 100 的**增量修正批**，不改变 100 的用户故事、账号模型、协议契约、端到端加密模型与配额纪律（推 / 拉频次口径不变）。100 的 §4 FR-006（版本号机制）与 §6 AC-08 / AC-09（合并收敛）**继续有效**：本项只改「版本号从哪来」，不改「版本号怎么比」。
- **ADR 0076**：D2-5 的「待授权」措辞由 **D2-5a** 取代；本批**只实施 D2-5a**（a-1 … a-8），不触碰 D2-1 / D2-2 / D2-3 / D2-4 / D3-* / D4-*（服务端决策逐字未动）。
- **ADR 0076 D2-6（侧车落点加固）**：属 BR-①d，本批**不做**；本项不新增用户数据文件 ⇒ 不扩大该议题的落点面。
- **批次 BR-②（写预算护栏改全局口径）**：需用户拍板，本批**不做**；本项与该口径正交（护栏是「单账号刹车」，本项是「消除放大源」）。
- **批次 BR 探针与配额事故**：生产写入额度耗尽属独立事故议题，本批只**读**其状态用于取证（不执行清理、不改阈值、不部署）。
