# 101 · Spec · 云同步「远端版本沿用」（删除本地同步状态后不再重写云端）

> 立项时间：2026-11-24。状态：**设计已定案，待实施**。
> 前置：spec `100-fluxing-cloud-account-sync`（云端账号与多端同步，已上线）；批次 BR（`docs/adr/0076-cloud-write-amplification-governance-and-zero-write-registration.md`）。
> 规范来源：ADR 0076 的 **D2-5a** 段（a-0 … a-8）—— 本文件的需求**逐条对齐**该段，映射表见 §9。
> 授权：用户 2026-11-24 已明确授权客户端改动（批次 BR-①c）。
> 本文件只讲**用户能得到什么**；技术方案在 `plan.md`，执行序在 `tasks.md`。

## 1. 任务目标（一句话）

让「本机同步状态丢失（换机、重建用户数据目录、手工删除同步状态文件）」**不再把云端整份词库重写一遍** —— 同步一次之后，云端该写的行数必须是 **0**。

## 2. 用户故事

| # | 故事 | 验收一句话 |
|---|---|---|
| **US1** | **换机不重写云端**：我换了台电脑，同步一次不该把云端整份词库覆盖一遍 | 换机后首次同步，云端词库条数与内容**逐条不变**，云端存储写入增量为 0 |
| **US2** | **重建用户数据目录不炸配额**：我清过用户数据目录，现在同步别再把云端写爆 | 重建目录后同步一次，云端写入行数为 0；不会再出现「写入额度用尽 ⇒ 登录 / 同步失败」 |
| **US3** | **本地与云端一致时不动云端**：两边本来就一样，同步就该什么都不做 | 本地与云端内容一致时同步，本地词条不被改动、云端不被改写 |
| **US4** | **我新加的词照样上云**：优化不是「不让我同步」 | 本地新增 / 修改的词条**仍能正常上传**，不被「延迟」吞掉 |
| **US5** | **两台设备同时改过**：分歧条目的结果与现在一致 | 同一条目两端都改过时，行为与优化前**完全一致**（本地胜出），不丢我的改动 |
| **US6** | **同步过程无感**：优化不许拖慢打字 | 同步全程在后台；输入延迟与上屏耗时与优化前无可感知差异 |
| **US7** | **看得见摸得着的证据**：出了事我能查日志 | 每轮同步都有一行固定格式的诊断记录，能直接看出「扫完没有 / 对上几条 / 压后几条 / 分歧几条 / 推了几条」 |

## 3. 范围

### 3.1 适用范围

| 项 | 结论 |
|---|---|
| 触发场景 | 本地同步状态文件缺失 / 被重置（换机、重建用户数据目录、手工删除）后的**首次**同步 |
| 作用对象 | 用户词库条目（`type=userdb`）的**逐条**版本沿用 |
| 作用位置 | 仅**本机客户端**的同步协调器与本地同步状态文件 |
| 服务端 | **一字不改**（不改协议、不改数据库、不重新部署） |

### 3.2 明确不改（红线）

- 不改服务端任何一行代码、不改服务端接口契约、不改服务端数据库结构 ⇒ **无需重新部署**。
- 不新增进程间通信消息类型 ⇒ 不触发「协议四边同步」流程。
- 不改动引擎子模块。
- 不改本地同步状态文件的**格式**（不新增行、不新增字段、不新增版本行，**不扩展既有字段的取值域**）。
- 不新增用户数据文件（状态不落新文件）。
- 不新增第三方依赖。

### 3.3 本批明确不做

- 不修「口令轮换 ⇒ 全量重推」（密钥变了 ⇒ 云端旧条目解不开 ⇒ 本质不可免）。
- 不修「分歧条目本地胜出」可能覆盖另一台设备更新版本的既有风险。
- 不把服务端写预算护栏从「每账号」口径改成「全局」口径（另一批次 BR-② 议题）。
- 不做「删条目」云端接口；云端已有的脏条目不在本项范围。
- 不升级付费套餐（另需用户拍板）。

## 4. 功能需求

| # | 需求 | 对齐 |
|---|---|---|
| **FR-001** | 一轮同步的固定顺序必须是「导出本地 → **拉取远端** → 定版本 → 合并 → 回写本地 → 推送 → 更新本地同步状态」；**版本号的分配 / 复用必须发生在拉取远端之后**（否则本机看不到远端版本 ⇒ 无从沿用）。 | a-1 |
| **FR-002** | 本地条目与本轮远端条目**同键**且**明文载荷逐字节相等**时：沿用**远端版本号**、**不标记本地改动**、**不进入推送集合**、在本地同步状态文件里记「远端版本号 + 载荷哈希」⇒ 该条目本轮**零写入**。 | a-2 |
| **FR-003** | 「是否同一条」的判别条件**只能**是「解密后的明文载荷逐字节相等」；**不得**用「版本号相等」「密文相等」「长度相等」「哈希近似」等条件代替。 | a-2 |
| **FR-004** | 本轮结束时服务端**仍报告「还有更多」**（= 本轮没把云端库存扫完）⇒ 本轮**不得**推送「既无本地同步状态记录、又不在本轮远端集合里」的本地条目（延后到库存扫完后的轮次）。闸门在「库存扫描未完成」期间**逐轮持续生效**；ADR a-3 的字面条件（拉取起始游标 = 0）是本条的**子情形**，本批取**超集**口径（依据与副作用见 `spec.md` §8-6、`plan.md` §4.3）。 | a-3 + a-8① |
| **FR-005** | 本地同步状态文件的**格式逐字不变**（不新增行 / 字段 / 版本行，**不扩展既有字段的取值域**）；「库存是否扫完」**不落盘** —— 每轮由服务端当场回答 ⇒ 本批**零新增状态面**。 | a-3 |
| **FR-006** | 「远端版本沿用」命中的条目 + 「远端胜出」的条目，都要写入本地同步状态文件且携带**远端版本号**；扫描期间**逐轮重建**状态文件 ⇒ 扫描完成后回到常规增量行为。 | a-4 |
| **FR-007** | 同键但明文载荷**不同** ⇒ 分歧，分两个子情形：① 本地同步状态**有**该键的记录且载荷哈希**未变**（本地没改过）⇒ **远端胜出、不回推**；② 本地同步状态**无**该键的记录（本地同步状态已丢失）或本地**改过**（哈希变了）⇒ **本地胜出**（分配新墙钟版本号 + 推送）。两子情形均与优化前行为**逐字一致**。 | a-5 |
| **FR-008** | 每轮同步**无条件**打印一行诊断记录：`[cloudsync] reconcile scan_complete=<0\|1> matched=<n> deferred=<n> divergent=<n> pushed=<n>`；本轮失败也照打。 | a-6 |
| **FR-009** | 客户端沿用远端版本号后，服务端的版本守卫必然命中（存储版本 ≥ 入参版本 ⇒ 跳过）⇒ 不写对象存储、不写数据库索引、不推进服务端序号。**客户端不得绕过该守卫**（不得给「沿用」的条目重新分配版本号）。 | a-2 / a-0 |
| **FR-010** | 判据取证必须**同时**给出三项：数据库 `sync_items` 今日写入增量 = **0**；`sync_items` 行数增量 = **0**；服务端拉取自愈删除（`handlePull` 的 `healed` 分支）**为空** —— 自愈删除同样计入写入。 | a-7 |
| **FR-011** | 判据场景 = 本地内容与云端内容一致（同一账号、已同步过的词库）。本地确有云端没有的新条目时，`sync_items` 行数增量 = 新增条目数（属**正常新增**，不计为写放大）；判据记录必须如实区分两者。 | a-7（场景界定） |
| **FR-012** | 本项**不改服务端** ⇒ 无需重新部署；但必须完成**出包装机 + 装机实证 + 真机判据复验**三步才算交付。 | a-8④ |

## 6. 验收标准

| # | 用例 | 通过条件 |
|---|---|---|
| **AC-01** | 删除本地同步状态文件后同步一次（US1 / US2 / FR-010） | `rows_written_24h` **增量 = 0** 且 `sync_items` **行数增量 = 0**（优化前 ≈ 40,061 行）；服务端 `healed` 自愈删除**为空** |
| **AC-02** | 本地同步状态完好时的常规同步（US3 / FR-001） | 行为与优化前**逐字一致**：只推「本地改动过」的条目；未改动条目不上传 |
| **AC-03** | 本地确有改动（US4 / FR-007） | 新增 / 修改的本地词条仍能被推送成功并落库（本地与云端确实不同的条目照常上云） |
| **AC-04** | 两端分歧条目（US5 / FR-007） | 同键不同内容时：本地同步状态完好且本地未改 ⇒ 远端胜出、不回推；本地同步状态丢失或本地改过 ⇒ 本地胜出并推送成功 —— 两子情形均与优化前结果一致 |
| **AC-05** | 诊断记录（US7 / FR-008） | 成功轮与失败轮都能抓到 `[cloudsync] reconcile ...` 一行，且五个字段齐全、取值与本轮实际一致 |
| **AC-06** | 单测覆盖（FR-002 / FR-003 / FR-004 / FR-006） | 判别性单测覆盖：明文逐字节相等 ⇒ 沿用且不推；明文不同 ⇒ 分歧本地胜出；库存未扫完 ⇒ 未证实条目被压后；本地同步状态重建携带远端版本号 |
| **AC-07** | 门禁（宪法 II / R6） | 客户端单测全绿且用例数不减；云端单测基线不变；格式检查零漂移；改动文件无乱码字符 |
| **AC-08** | 出包装机 + 装机实证（FR-012） | 安装包载荷与构建产物逐字节相等；装机后进程、用户数据目录、登录态均未被破坏 |
| **AC-09** | 真机判据复验（AC-01） | 在真机上删除本地同步状态文件 → 触发同步 → AC-01 三项全部成立 |

## 7. 合规红线

1. **输入内容永不上云**：只有用户自己造出来的资产进入同步管道（沿用 spec 100 红线 1）。
2. **云端不见明文**：沿用远端版本的判别发生在**解密后**的本地内存里，明文不离开本机（沿用 spec 100 红线 2）。
3. **默认关**：不登录即零出向请求（沿用 spec 100 红线 3）。
4. **不自造遥测**：本项新增的诊断记录只进本地日志，**不上报**。
5. **不碰第三方端点**：沿用 spec 100 红线 5。
6. **离线优先**：任何网络故障都不允许阻断本机使用（沿用 spec 100 红线 6）。

## 8. 已知边界（如实登记，本批不修）

1. **单轮拉取上限 1,000 条**（服务端单页 100 条 × 客户端单轮 10 页）⇒ 大账号的库存扫描需**多轮**才能扫完；**扫描未完成的轮次零写入** ⇒ 新增词条的上云会被**延迟**到扫描完成之后（延迟，不丢数据）。
2. **分歧条目本地胜出的既有风险不修**：本地同步状态丢失后丧失「按版本定序」能力，可能覆盖另一台设备的更新版本（a-5 代价）。
3. **口令轮换路径本质不可免**：密钥变了 ⇒ 条目身份变了 ⇒ 云端旧行解不开 ⇒ 全量重推（不在本项范围）。
4. **本地同步状态文件仍会丢失**：本项只保证「丢了之后不重写云端」，**不保证**「不会丢」⇒ 落点加固属另一议题（BR-①d）。
5. **取证受生产写入额度影响**：若生产数据库当日写入额度已耗尽，推送会被服务端拒绝 ⇒ 「零写入」与「被额度挡住」两种结果必须**分别取证**（见 `plan.md` §9）。
6. **实施解释（非缺陷，但必须知情 · 已登记待拍板）**：闸门口径取 a-3 的**超集** —— 触发条件只看「本轮结束时库存未扫完」（服务端仍报告「还有更多」），a-3 字面的「拉取起始游标 = 0」只是其**子情形**；解除条件 = 某轮 `has_more == false`（库存扫完）。依据：a-8①「扫描未完成的轮次零写入」与 AC-01 的判据（若闸门只覆盖首轮，第 2 轮起会把「本轮尚未见到」的本地条目当成新增推送 ⇒ 写放大原样复现 ⇒ 判据不成立）。**副作用如实登记**：本地同步状态完好但云端增量超过单轮拉取上限时，新增本地词条也会被**延后**到扫完那一轮（延迟，不丢数据）。「库存是否扫完」**不落盘**（每轮由服务端当场回答），扫描进度由**既有游标**推进承载 ⇒ 本地同步状态文件格式逐字不变（FR-005）。
